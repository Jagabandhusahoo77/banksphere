# ADR-006: Employee Identity and RBAC Foundation

**Status:** Accepted for Phase 9A

## Context

BankSphere has, until this phase, been a single-channel product: a customer-facing internet-banking portal backed by four microservices, all trusting one kind of identity (a customer, authenticated via customer-service's JWT). This phase begins a second, structurally separate channel — an internal bank-operations platform for BankSphere employees (tellers, KYC/loan/card officers, branch managers, admins) — without touching or duplicating the customer-facing system, and without yet building any operational capability (no KYC, loans, cards, cash operations, audit service, or Kafka — those are explicitly future phases). This phase is identity and authorization only: who is an employee, what can they do, and how is that enforced.

## Decision 1 — The employee portal is a separate frontend application, not a new area of the customer app

`employee-portal/` is its own Vite/React/TypeScript application — separate `package.json`, separate dev server port (5174 vs the customer portal's 5173), separate Docker image/nginx container, separate `localStorage` key (`banksphere.employee.auth` vs `banksphere.auth`), separate `AuthContext`/`ProtectedRoute`/routing tree entirely.

**Why not a `/employee` section inside the existing customer frontend:** the entire point of this phase's security boundary is that an employee session and a customer session must never be conflatable. Two apps sharing one codebase's routing tree, one bundle, and one set of contexts creates exactly the kind of surface where a shared piece of state (a stale `AuthContext`, a shared axios instance, a shared token key) could leak across the boundary through an ordinary refactor six months from now. Two genuinely separate applications make that class of bug structurally impossible, not just disciplined-against. They do share the same visual design tokens (`tailwind.config.js`'s brand/semantic/surface/ink palette, the same logo) — it's the same fictional bank, just two different front doors — but share no code, no build, no runtime state.

## Decision 2 — Employee JWTs are signed with a separate key from customer JWTs, not just a separate claim

This was the central security question this phase posed explicitly, and it was not resolved by convenience. The customer-facing services (customer/account/transaction/beneficiary) all share one HS256 signing secret, `JWT_SECRET` — that sharing was always safe because they're all validating the *same* principal type (a customer) for the *same* trust domain. Employee identity is a different principal type entirely, and reusing `JWT_SECRET` for it was considered and rejected:

- **The alternative considered**: reuse `JWT_SECRET`, and have employee-service distinguish a customer token from an employee token purely by claim shape (e.g. a `"roles": ["ROLE_CUSTOMER"]` vs `"roles": ["TELLER"]`, or a dedicated `principalType` claim). This would technically work as long as every employee endpoint correctly checked that claim.
- **Why it was rejected**: that "as long as" is exactly the failure mode this phase's own instructions called out — *"Do not simply add EMPLOYEE to the existing customer role list and call the problem solved."* A claims-only distinction means a customer's already-valid, already-signed JWT is cryptographically indistinguishable from a forged one at the signature-verification step — the *only* thing standing between "customer token" and "employee token" is that every single current and future employee endpoint remembers to check a claim correctly. One missed check, one new endpoint added six months from now that forgets it, and a customer session becomes a valid credential against the employee portal.
- **What was built instead**: employee-service reads its signing key from a wholly separate environment variable, `EMPLOYEE_JWT_SECRET` (also ≥32 bytes, same fail-fast startup check as every other service's `JWT_SECRET`, per CLAUDE.md's JWT rule — see `security/JwtService`'s constructor). A customer JWT, signed with `JWT_SECRET`, fails signature verification outright the moment it's presented to employee-service — `Jwts.parser().verifyWith(employeeKey)...` throws before any claim is ever inspected. This is proven directly (not just asserted) in `JwtServiceTest.parseClaims_returnsEmpty_forTokenSignedWithADifferentKey_modelingACustomerJwt`, which builds a real token with a different real key and confirms employee-service's `JwtService` rejects it outright.
- **A second, independent layer, for defense in depth**: even with a separate key, `JwtService.generateToken` also stamps a `principalType: "EMPLOYEE"` claim, and `JwtAuthenticationFilter` only authenticates a parsed token if `JwtService.isEmployeeToken(claims)` is true. This is deliberately *not* the primary defense (a customer token never reaches this check at all, since it fails key verification first) — it exists so that even a future configuration mistake that accidentally pointed both services at the same secret would still require an attacker to forge a claim they have no way to sign, not just replay an already-valid token.

The consequence: `EMPLOYEE_JWT_SECRET` is a new, separate local-dev default in `docker/local/.env.example`, alongside (never instead of) `JWT_SECRET`. Rotating one has zero effect on the other.

## Decision 3 — Employee identity/authorization data lives in its own service and database; no core banking data is duplicated

`employee-service` (port 8085, `banksphere_employee` database) owns exactly `Employee`, `Branch`, and the `employee_roles` join table — nothing about customers, accounts, or transactions. It has no foreign key, no read replica, no cached copy of any core-banking table. When a future phase needs an employee to *act on* a customer's account (a teller processing a cash deposit, say), the call path is:

```
Employee Portal → Employee-facing API → account-service → account database
```

never:

```
Employee Portal → employee database → account database
```

This phase builds no such operational call at all (explicitly out of scope), but the shape is decided now so the next phase doesn't have to re-litigate it: employee-service's job is authentication and authorization, never a second source of truth for banking data. This mirrors the same database-per-service, no-cross-service-FK principle already established for customer-service/account-service/transaction-service/beneficiary-service.

## Decision 4 — RBAC is enforced with `@PreAuthorize` against permissions, server-side, on every endpoint that needs it — never by hiding a nav item

Permissions (`CUSTOMER_VIEW`, `CASH_DEPOSIT`, `KYC_APPROVE`, `EMPLOYEE_MANAGE`, ...) are defined as an enum, independent of `Role`. `security/RolePermissions` is a single, authoritative, code-defined `Map<Role, Set<Permission>>` (see `docs/architecture/employee-platform.md` for the full table); `JwtService` computes an employee's effective permission set at token-issue time and embeds it directly in the JWT (`permissions` claim), so every downstream authorization decision reads straight off the token rather than re-querying the database per request. `EmployeeController`'s admin endpoints are annotated `@PreAuthorize("hasAuthority('EMPLOYEE_MANAGE')")`; `SecurityConfig` enables `@EnableMethodSecurity` for exactly this purpose — the one deliberate difference from every other service's `SecurityConfig`, which only ever gates on "authenticated or not."

The employee-portal frontend also has a `RequirePermission` route guard and a permission-filtered "Your access" list on the Profile page — but both are explicitly documented (in their own source comments and in `docs/architecture/employee-platform.md`) as UX conveniences only. The backend's `@PreAuthorize` checks are what actually make a request fail with 403; nothing about hiding a button changes what the API will accept. This was proven, not just claimed: `EmployeeControllerTest` includes a parameterized test (`createEmployee_returns403_forEveryNonAdminRole`) that authenticates as every non-`ADMIN` role in turn and confirms the server rejects each one with 403 regardless of what any frontend would or wouldn't have shown them.

**A real bug found and fixed while writing these RBAC tests**: `GlobalExceptionHandler`'s existing catch-all `@ExceptionHandler(Exception.class)` (the same boilerplate pattern every other service uses) was silently swallowing Spring Security's `AccessDeniedException` — thrown by `@PreAuthorize` — before `JwtAccessDeniedHandler` (the class actually responsible for producing the 403 response) ever saw it, turning every intended 403 into an unexplained 500. This is the same *class* of bug CLAUDE.md already documents for `@AutoConfigureMockMvc(addFilters = false)` — a piece of infrastructure that looks like it's just generic scaffolding quietly defeats a specific security mechanism. Fixed by adding an explicit `@ExceptionHandler(AccessDeniedException.class)` returning 403. Recorded here because none of the four existing services had ever exercised this path before (none of them use `@PreAuthorize`), so the bug had no prior opportunity to surface.

## Decision 5 — Roles are many-to-many; permission mapping is code-defined, not yet database-editable

An `Employee` can hold more than one `Role` (`@ElementCollection<Role>` against a fixed enum, backed by an `employee_roles(employee_id, role)` join table) — a branch manager who's also a trained teller is a realistic scenario the schema should not force around. The `Role → Set<Permission>` mapping itself, however, is a static `Map` in Java (`RolePermissions`), not a database table. This was a deliberate scope decision: `ROLE_MANAGE` exists as a permission name (implying a future capability to edit that mapping), but building the database schema, admin UI, and cache-invalidation-on-change logic for a *live-editable* mapping is meaningfully more than "employee identity + RBAC foundation" — it's the next phase's work, once there's an actual admin screen to drive it from. Recorded as deferred, not silently skipped.

## Decision 6 — No public employee registration; a single seeded bootstrap admin closes the chicken-and-egg problem

`POST /api/v1/employees` requires `EMPLOYEE_MANAGE`, held only by `ADMIN`. With no public registration and no pre-existing employee, nothing could ever create the first one — so `V2__seed_bootstrap_branch_and_admin.sql` seeds one `HQ001` branch (IFSC `BANK0000001`, matching account-service's own constant — see `AccountServiceImpl.BANKSPHERE_IFSC`) and one `ADMIN` employee (`admin` / `ChangeMe123!`, a real BCrypt hash generated out-of-band with this service's own `BCryptPasswordEncoder` and round-trip-verified before being committed as a migration literal — Flyway migrations can't call application code, so the hash has to be precomputed). This mirrors the project's existing local-dev-only-default-credentials convention (`docker-compose.yml`'s own `banksphere`/`banksphere_local_dev`, sanctioned by CLAUDE.md) and carries the same obligation: rotate or deactivate this account before any real/shared deployment. It is not a backdoor left undocumented — it's the explicit, single, auditable seam by which the system bootstraps itself, and every login through it is captured by the same structured audit line (`EmployeeAuditLog`) as any other employee's login.

## Decision 7 — Audit-ready structured logging now; a real Audit Service later

Every login attempt (success or failure) and every employee-management action (create, status change) is logged as one structured line via a dedicated `AUDIT` logger (`EmployeeAuditLog`), carrying `employeeId`, `employeeNumber`, `action`, `result`, `timestamp`, and a request `correlationId` (attached by a new `CorrelationIdFilter` — from the caller's own `X-Correlation-Id` header if present, else freshly generated, and echoed back in the response so a caller can correlate their own request to this log line). This is deliberately *not* the Audit Service named in the project roadmap — no new database table, no Kafka topic, no query API. It's the minimum shape a future log-shipper (Fluent Bit/OpenSearch, per the roadmap) or a real Audit Service could consume without reparsing free-text messages, built now because retrofitting structure onto unstructured logs later is far more expensive than logging structurally from day one. A failed-login line deliberately omits `employeeId`/`employeeNumber` for an unknown username (only the attempted username, already caller-supplied input) — logging them would turn the audit trail itself into a username-existence oracle for anyone who could read it.

## Decision 8 — Branch is minimal on purpose; branch-scoped authorization is a documented future step, not a present one

`Employee.branch` is populated and appears on the JWT (`branchId` claim) and in every response, but no endpoint in this phase filters or restricts anything by it — an `ADMIN` can currently list every employee regardless of branch, for instance. Building real branch-scoped authorization (a `BRANCH_MANAGER` can only manage employees at their own branch, a `TELLER`'s future cash-operation endpoints only see their own branch's queue, etc.) requires deciding, per-permission, whether it's branch-scoped or global — that's a design question tangled up with the operational endpoints this phase explicitly doesn't build yet. Recorded here as the next concrete security step once those endpoints exist, not deferred silently: **the branch id is already flowing through the token today specifically so that future authorization logic has it available without a second lookup.**

## Consequences

- Two fully separate frontend applications now exist (`frontend/`, `employee-portal/`), two separate signing keys, two separate databases-per-identity-type — no shared runtime state between the customer and employee channels anywhere.
- `EmployeeController`'s admin endpoints are the first `@PreAuthorize`-gated endpoints in this codebase — `@EnableMethodSecurity` and the `AccessDeniedException`-handling fix are now part of the established pattern for any future service that needs permission-level (not just authentication-level) checks.
- The `RolePermissions` table is the single source of truth for "who can do what" in this phase — any future endpoint (KYC, loans, cards, cash operations) should be gated against a `Permission` from this same enum, not a new ad hoc check.

## Deferred to a later phase

Database-backed, admin-editable role→permission mapping (the actual use of `ROLE_MANAGE`); branch-scoped authorization enforcement; the real Audit Service (Kafka-backed or otherwise) consuming `EmployeeAuditLog`'s structured lines; any operational employee-facing endpoint (KYC review, loan/card approval, cash deposit/withdrawal, service-request processing, transaction investigation) — all explicitly out of scope per this phase's own repeated instruction, and none of the groundwork laid here (permissions enum, branch id on the token, correlation ids) was built speculatively beyond what this phase's own identity/RBAC boundary required.
