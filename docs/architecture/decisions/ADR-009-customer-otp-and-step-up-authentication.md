# ADR-009: Customer OTP Authentication and Step-Up Authentication

**Status:** Accepted for Phase 9D

## Context

Phases 8B/9A/9B/9C left customer-service authentication exactly as ADR-002 (Phase 3A) designed it: email + password → a single JWT access token, no refresh mechanism, no second factor, no revocation. Employee identity (ADR-006) and customer identity have been kept on deliberately separate signing secrets throughout — that boundary must be preserved here, not touched.

This phase's requirement, before cash withdrawal/payments/loans/cards/forex are built: production-style customer OTP login, plus step-up authentication for high-risk operations (starting with transfers above a configurable threshold). Two explicitly distinct flows — **customer login OTP** and **step-up OTP for an already-authenticated customer performing a sensitive operation** — must never be conflated. Redis, Kafka, a real SMS/email/WhatsApp provider, AWS infrastructure, and building out withdrawal/cards/loans endpoints are all explicitly out of scope (see `docs/00-project-overview/scope.md`).

## Decision 1 — OTP domain lives in customer-service, not a new `banksphere_identity` service

The phase's own instructions required inspecting whether customer-service already owns authentication before adding a second implementation. It does — registration, credentials, JWT issuance, `/login`, `/logout`, `/me` are all here. OTP is a new authentication *factor* within that same bounded context, not a new domain. A dedicated identity service would duplicate that ownership for no benefit at this scale, the same reasoning ADR-002 already used to reject a separate `auth-service`. Banking-domain services (account/transaction/kyc/beneficiary) never generate or validate an OTP themselves — they only consume the identity and, for account-service, the step-up confirmation this phase adds.

## Decision 2 — Two distinct flows, never conflated: `OtpPurpose.LOGIN` vs `OtpPurpose.STEP_UP_*`

One `OtpChallenge` entity, one `OtpService`, but the two flows never share code paths that matter for security:

- **LOGIN** (`requestLoginOtp`/`verifyLoginOtp`): identifies a customer from an *unauthenticated* request (email or phone), issues a full session (access token + refresh cookie) on success.
- **STEP_UP_TRANSFER** (`requestStepUp`/`verifyStepUp`/`confirmStepUpExecution`): the customer is *already authenticated* (JWT required); this proves intent for one specific operation, never issues a new session, and terminates in `EXECUTED` — a state LOGIN's `CONSUMED` never reaches.

`OtpPurpose` also defines `STEP_UP_WITHDRAWAL`, `STEP_UP_BENEFICIARY`, `STEP_UP_PROFILE_CHANGE` — real enum values with real javadoc, since the task explicitly named them as future policy consumers, but only `STEP_UP_TRANSFER` is accepted by `requestStepUp` this phase (any other `STEP_UP_*` purpose is rejected with 400). See Decision 12.

## Decision 3 — OTP generation and hashing

`OtpGenerator` uses `SecureRandom` exclusively — never `java.util.Random`, a UUID substring, a timestamp, or anything derived from customer/account data — producing a zero-padded numeric string built digit-by-digit (never round-tripped through an `int`, which would silently drop leading zeros). The generated code is hashed with the same `PasswordEncoder` (BCrypt) bean `SecurityConfig` already exposes for password hashing — reused for consistency and constant-time comparison via `passwordEncoder.matches()`, rather than introducing a second hashing scheme for a second kind of secret. The plaintext OTP is held in memory only long enough to hash it and hand it to `OtpDeliveryProvider`/`DevOtpInbox` — never persisted, never logged (see Decision 16).

## Decision 4 — Challenge lifecycle: one state machine, purpose-dependent terminal states

```
PENDING → VERIFIED (step-up only) → EXECUTED (step-up only, downstream operation actually ran)
PENDING → CONSUMED (LOGIN's terminal success state — nothing further to authorize)
PENDING / VERIFIED → EXPIRED | LOCKED (failure states)
```

A LOGIN challenge never becomes `VERIFIED` — correct OTP entry *is* the whole transaction, so it goes straight to `CONSUMED`. A step-up challenge's correct OTP entry only proves "the customer entered the code correctly" — the challenge still has to authorize exactly one downstream operation (Decision 12) before it's truly done, hence the extra `VERIFIED`/`EXECUTED` states LOGIN doesn't need.

## Decision 5 — Expiration, brute force, and "never reset attempts by requesting a new OTP"

`OtpProperties` (all configurable, all defaulted for local dev): 6-digit codes, 300s expiry, 5 max attempts, 30s resend cooldown, 300s step-up-verified window. `validateAndConsume` is the single shared verify path for both LOGIN and step-up: checks consumed/executed → locked → expired → attempts-remaining → hash match, incrementing `attemptCount` on any miss and flipping to `LOCKED` once attempts are exhausted. Requesting a fresh OTP for the same identifier+purpose never resets an existing challenge's attempt counter — `supersedeExisting` marks the *old* `PENDING`/`VERIFIED` row `EXPIRED` and a genuinely new row starts at `attemptCount = 0` legitimately, because the old row is now permanently unusable, not reset.

## Decision 6 — Rate limiting is in-memory and explicitly not production-ready

`OtpRateLimiter` is a single-JVM sliding-window limiter (`ConcurrentHashMap<String, Deque<Instant>>`), applied per-IP to four buckets (`otp-request`/`otp-verify`/`step-up-request`/`step-up-verify`) independently. **This provides no real protection the moment this service runs behind more than one replica** — its own javadoc says so explicitly, and this ADR repeats it per CLAUDE.md's honesty requirement: production deployment needs distributed rate limiting (Redis sliding-window/token-bucket), which is out of scope until Redis's own designated phase.

## Decision 7 — Account enumeration prevention, extending an existing pattern rather than inventing a new one

`AuthServiceImpl.login()` already defended against enumeration via a `DUMMY_PASSWORD_HASH` compared even when no customer matches, so a wrong-password and an unknown-email response take the same rough time. `requestLoginOtp` does the equivalent: it **always** creates a real `OtpChallenge` row and generates/hashes a real OTP, regardless of whether the identifier matched a real, enabled customer — `customerId` is simply `null` on the challenge when it doesn't. `OtpDeliveryProvider.deliver()` is only actually called when a real customer was found, but the HTTP response (`"If the account is eligible, an OTP has been sent."` + a real `challengeId`) is identical either way. `validateAndConsume` additionally checks `challenge.getCustomerId() != null` as defense-in-depth, so verification can never succeed for a no-match challenge even in a hypothetical hash-collision scenario. Verification errors are equally generic — one `InvalidOtpException` ("Invalid or expired OTP") for wrong code, expired, already-used, and locked alike, mirroring `InvalidCredentialsException`'s reasoning exactly.

## Decision 8 — Mock delivery provider + a dev-only OTP inbox, gated at the bean level

`OtpDeliveryProvider` is an interface; `MockOtpDeliveryProvider` (the only implementation this phase) logs `[MOCK OTP DELIVERY] purpose=... identifier=**** otp=...` with the identifier masked. `DevOtpInbox` keeps the last 50 delivered codes in memory purely for local development/testing convenience, reachable only via `DevOtpInboxController` — which carries `@ConditionalOnProperty(prefix = "banksphere.otp.dev-inbox", name = "enabled", havingValue = "true")`. **This means the controller bean, and therefore the route, does not exist in the application context at all when disabled** — a 404 from Spring's own "no handler found," not a runtime permission check a future change could weaken. Verified directly (not just asserted) via `DevOtpInboxControllerTest`'s `ApplicationContextRunner` tests. Defaults to enabled for local Docker Compose; **must be `false`, or the feature not deployed at all, in any real environment.**

## Decision 9 — Future delivery providers (documented, not built)

`OtpDeliveryProvider` is the seam a real provider plugs into without touching `OtpServiceImpl`: `OtpService → OtpDeliveryProvider → {Mock (today), SMS, Email, WhatsApp (future)}`. No paid provider (Twilio, WhatsApp Business API, SES) is integrated this phase — explicitly out of scope. A later phase's Notification Service would sit behind this same interface (`Auth Service → Notification Service → SMS/Email/WhatsApp`) without changing any auth business logic.

## Decision 10 — Access token strategy: unchanged JWT, one new shared issuance path

No change to `JwtService`/`JwtProperties`/token *shape* (`sub`, `email`, `roles: ["ROLE_CUSTOMER"]`, `JWT_SECRET`, ≥32 bytes, fail-fast). What's new is `AuthService.issueAccessToken(UUID customerId)` — a shared tail-end `login()` (password), `verifyLoginOtp` (OTP), and `token/refresh` (rotation) all call, so there is exactly one place that turns "identity already proven some other way" into a signed token. It never re-checks a password or any other credential; `AuthServiceImpl.login()` itself was refactored to extract a private `issueAuthResponse(Customer)` helper that both `login()` and `issueAccessToken()` now share.

## Decision 11 — Refresh token strategy: opaque, HttpOnly-cookie-only, rotation with reuse detection

**Opaque, not a JWT.** 32 random bytes, Base64 URL-safe, generated fresh on every issuance — never a self-describing token, since a refresh token needs no claims, only a lookup key. **SHA-256, not BCrypt**, for the stored hash: the token is already 256 bits of entropy, so a slow salted hash defends against nothing a fast hash doesn't already, and BCrypt would only add unnecessary CPU cost. **Delivery: HttpOnly cookie only** (`banksphere_refresh_token`, path `/api/v1/auth`, `SameSite=Lax`, `Secure` conditional on `COOKIE_SECURE`, default `false` for local HTTP) — never in a JSON response body, never reachable from frontend JavaScript. `SameSite=Lax` (not `None`) was chosen because `localhost:5173` (frontend) and `localhost:8081` (customer-service) are different ports but the same registrable domain — same-site for cookie purposes even though cross-origin for CORS purposes — avoiding the `Secure`/HTTPS requirement `SameSite=None` would impose and that would break local HTTP dev. This is also the actual CSRF defense for the two cookie-bearing endpoints (`/token/refresh`, `/logout`): a browser will not attach a `Lax` cookie to a cross-site POST, so Spring Security's CSRF protection stays disabled, as documented directly in `SecurityConfig`'s class javadoc.

**Rotation + reuse detection** (the standard algorithm): every successful `/token/refresh` call revokes the presented token (`ACTIVE → ROTATED`, linked to its successor via `replacedByTokenId`) and issues a new one. Presenting an already-`ROTATED` token again is treated as a theft signal — it revokes **every** active token for that customer (`revokeAllForCustomer`), logs `OtpAuditLog.refreshTokenReuseDetected`, and throws the exact same generic `RefreshTokenInvalidException` (401) any other invalid-token case produces. The response never distinguishes "this was theft" from "this token simply expired."

**A real bug, found via live Docker verification and fixed before shipping:** the family-wide revocation was originally a private method inside `RefreshTokenService.rotate()`, mutating entities in the *same* `@Transactional` method that then threw `RefreshTokenInvalidException` two lines later. Spring's default rollback-on-`RuntimeException` behavior silently rolled back that entire transaction when the exception propagated — undoing the revocation it had just performed, while still correctly rejecting the one request that triggered it. The theft-detection guarantee was therefore completely inert: a stolen-and-replayed token's siblings stayed `ACTIVE`. This was caught by curling a real running container through the exact reuse sequence and inspecting the database afterward (see the Phase 9D engineering journal entry), not by any unit test — the unit tests mocked the repository and never exercised a real Spring transaction boundary. **Fix:** the revocation was extracted into `RefreshTokenRevocationService`, a separate `@Component` bean with its own `@Transactional(propagation = Propagation.REQUIRES_NEW)` method, called through the Spring proxy from `rotate()` — the exact same pattern (and the exact same reason) `TransferIdempotencyService` in account-service already uses for its own bookkeeping (see Decision 15). Re-verified live afterward: a stolen token's sibling is now correctly rejected on its next use.

## Decision 12 — Step-up authentication is not login, and is not a broad trust window

An already-authenticated customer can still need to prove intent again before a specific sensitive operation. The task's instructions were explicit and this ADR repeats the constraint verbatim: **do not** implement "OTP verified → trusted for the next N minutes." A step-up challenge authorizes exactly one, already-fully-specified operation — never a time window, never a category of future operations. `requestStepUp` requires the caller's own JWT (`CurrentUser.id`, never a body field) and a `TransferStepUpContext` describing the exact operation; the resulting challenge is bound to both the customer and that operation (Decision 13). A customer cannot request step-up for ₹1,000 and later spend the resulting authorization on a ₹100,000 transfer, or on anyone else's transfer.

## Decision 13 — Operation binding: `OtpContextHasher`, not a generic JSON diff

The mechanism behind "request OTP for ₹1,000, then submit ₹100,000 must fail": `OtpContextHasher.hash(List<String> canonicalParts)` computes a SHA-256 hex digest over an **explicitly ordered** list of canonical strings — for a transfer, `[sourceAccountId, destinationAccountNumber, destinationIfsc, amount.stripTrailingZeros().toPlainString(), currency]`, joined with the ASCII unit-separator `0x1F` rather than a printable delimiter (a free-text field could plausibly contain `,` or `|`; `0x1F` cannot plausibly appear in a real account number, IFSC, or amount). **Deliberately not a generic JSON serialization** of an arbitrary object — JSON key ordering and number formatting are not guaranteed byte-identical across two independent recomputations in two different services (customer-service at request/verify time, account-service's confirm call at execution time), and this hash must match exactly, twice. The hash is stored on `OtpChallenge.contextHash` at request time and **recomputed and compared** at `confirmStepUpExecution` — any mismatch throws `StepUpContextMismatchException` (403), even though the customer's JWT identity is still perfectly valid. Verified live: changing the amount *or* the recipient after step-up verification, before confirmation, is rejected with no balance mutation (see the Phase 9D engineering journal entry's FLOW 5 result).

## Decision 14 — Transfer integration: account-service remains authoritative, step-up is a prerequisite gate

`POST /api/v1/accounts/transfer` is not duplicated or bypassed. `AccountServiceImpl.transfer()` now wraps the pre-existing validation/mutation logic (unchanged — same account-ordering, optimistic-locking, best-effort-ledger design as ADR-004) with, in order: (1) an optional idempotency check (Decision 15), (2) every existing validation (ownership, active, currency, sufficient balance) unchanged, (3) — only after all of that passes — `StepUpPolicy.requiresStepUpForTransfer(amount)`; if true and no `stepUpChallengeId` was supplied, `StepUpRequiredException` (403); if supplied, `StepUpVerificationClient` confirms it with customer-service *before* any balance mutation. The frontend never decides step-up is satisfied — it only reacts to the 403 and displays the OTP UI; the backend is the sole authority, both for requiring step-up and for confirming it. The default threshold is ₹50,000 (`STEP_UP_TRANSFER_THRESHOLD`, configurable) — an illustrative BankSphere demo figure, not a real regulatory number.

**Cross-service confirmation authenticates via the customer's own token, not a shared secret.** `StepUpVerificationClient` forwards the caller's already-verified bearer token to customer-service's `POST /api/v1/auth/step-up/confirm` — the same "downstream service independently re-verifies the caller's real token" pattern this codebase has used since Phase 1 (ADR-001, ADR-007), now applied to a same-principal-type, cross-service confirmation rather than a customer→employee or employee→customer one. Unlike `TransactionClient` (best-effort, never rethrows — ADR-001), this call **must propagate failure**: an unreachable or erroring customer-service is never treated as "step-up satisfied," documented explicitly in the interface's own javadoc.

`StepUpPolicy` also defines `requiresStepUpForWithdrawal()`/`requiresStepUpForBeneficiaryCreation()` as real, testable methods (both currently `true`) — not yet wired to real enforcement call sites, since this phase's own testing checklist and all five browser/curl E2E flows are transfer-scoped only. A deliberate scope decision, not an oversight; documented here so a future phase wiring them in isn't duplicating unverified work.

## Decision 15 — Idempotency belongs to account-service, not the OTP/auth layer

Idempotency is a property of *executing an operation exactly once*, not an authentication concern — it lives in account-service, keyed on a client-generated `idempotencyKey`, customer-scoped (`UNIQUE (customer_id, idempotency_key)`). **The real enforcement is the database's own unique index**, not the application-layer `findBy...` check that precedes it (a concurrent second request can race past that check before either commits — the unique index is the actual backstop, surfaced as `IdempotencyConflictException` when `saveAndFlush` throws `DataIntegrityViolationException`). `TransferIdempotencyService` is a separate `@Service` bean using `@Transactional(propagation = Propagation.REQUIRES_NEW)` on every method specifically so its `IN_PROGRESS → COMPLETED/FAILED` bookkeeping survives the main transfer transaction's potential rollback — the same pattern Decision 11 describes fixing a bug by *not* having, in `RefreshTokenService`, until this phase. A `COMPLETED` record replays its cached `TransferResponse` snapshot verbatim rather than re-executing; `IN_PROGRESS`/`FAILED` both reject a same-key retry as a conflict, a deliberate simplification (retry-after-genuine-failure should use a fresh key) documented rather than silently allowed without test coverage. `idempotencyKey` is optional at the API level — a request that omits it gets no protection, but every real client (the frontend's own `Transfer.tsx`) always supplies one, generated once per review-step and reused across the step-up retry of the same logical attempt.

## Decision 16 — Audit: structured logs, one dedicated logger, secrets never included

`OtpAuditLog` mirrors `EmployeeAuditLog`/`KycAuditLog`'s established shape exactly — one dedicated logger (`com.banksphere.customer.AUDIT`), fixed key=value fields, `correlationId` from `CorrelationIdFilter`'s MDC entry (customer-service's first correlation-id filter, added this phase, matching the identical Phase 9A/9C pattern). Covers every required event: `OTP_REQUESTED`, `OTP_DELIVERED`, `OTP_VERIFICATION_SUCCEEDED`/`FAILED`, `OTP_EXPIRED`, `OTP_LOCKED`, `STEP_UP_REQUESTED`/`VERIFIED`/`FAILED`/`EXPIRED`/`EXECUTED`, `REFRESH_TOKEN_REUSE_DETECTED`. **Never logs**: the OTP value, a password, a refresh token, or an access token — every method takes a `challengeId`/`customerId`, never the secret those ids protect; `identifier` is masked to its last 4 characters everywhere it appears (the same convention `BeneficiaryServiceImpl` already uses for account numbers). This is not the real Audit Service from the roadmap — no Kafka, no new external system — a future Audit Service phase would consume these same structured lines rather than replace them.

## Decision 17 — Production, future MFA, and AI (documented only, not built)

**Production architecture** (future, not implemented): `CloudFront → WAF → ALB/API Gateway → EKS → Identity/Auth Service → OTP Provider`; `JWT_SECRET`/`EMPLOYEE_JWT_SECRET`/OTP config in AWS Secrets Manager or KMS-encrypted parameters, not environment variables; the rate limiter (Decision 6) backed by Redis/ElastiCache; audit lines (Decision 16) shipped to CloudWatch/CloudTrail instead of stdout. **Future MFA expansion**: this phase's OTP is a single, standard second factor; a real authenticator-app TOTP option, and treating step-up itself as a reusable building block for broader adaptive MFA policy, are natural extensions of the same `OtpChallenge`/`OtpPurpose` model, not a redesign. **AI** (future, not implemented, and never autonomous over security policy): login-anomaly detection, impossible-travel detection, unusual-device behavior, and adaptive/risk-based step-up thresholds are all plausible future consumers of the audit stream this phase already produces — any such system would only ever be able to *tighten* `StepUpPolicy`'s decision (require step-up where it otherwise wouldn't), never silently bypass a step-up requirement a human-configured policy would otherwise enforce.

## Consequences

- Customer login is now two paths (password, unchanged; OTP, new) issuing the identical `AuthResponse` shape, both now also setting the refresh-token cookie — no existing password-login test or UX changed.
- `banksphere_customer`'s schema gained two new tables (`otp_challenges`, `refresh_tokens`, `V3__add_otp_challenges.sql`); `banksphere_account` gained one (`transfer_idempotency_records`, `V3__add_transfer_idempotency.sql`).
- `CorsConfig.allowCredentials` flipped `false → true` in customer-service only (required for the browser to send/receive the refresh cookie cross-origin) — every other service's CORS config is unchanged and still `allowCredentials(false)`, since only customer-service ever sets or reads this cookie.
- `TransferRequest` (both account-service's DTO and the frontend's matching type) gained two new optional fields (`stepUpChallengeId`, `idempotencyKey`) — every existing test constructing it positionally needed updating; no existing behavior changed for a request that omits both.
- account-service gained its first cross-service call *into* customer-service (`CustomerServiceProperties`/`customerServiceRestClient`), alongside its existing one into transaction-service.
- A real security bug (Decision 11) was found only because live Docker verification was actually performed against running containers with real database inspection, not skipped as "environment doesn't support it" — recorded here as the concrete argument for why that step matters, not skipped, in every phase.

## Deferred to a later phase / Do NOT implement now

Cash withdrawal, payments, service requests, loans, cards, forex, international transfers, and notifications remain entirely out of this phase's scope, per the task's own instructions — `StepUpPolicy`'s withdrawal/beneficiary-creation methods exist but are not wired to real endpoints for exactly this reason. Kafka, an Outbox pattern, a Data Lake/Redshift, a real Notification Service, AWS/EKS infrastructure, and any AI implementation are documented in Decision 17 as future direction only. Distributed rate limiting (Redis) is a known, explicitly-stated gap (Decision 6), not solved here.
