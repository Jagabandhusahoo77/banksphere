# ADR-007: Branch Cash Deposit

**Status:** Accepted for Phase 9B

## Context

Phase 9A built employee identity, RBAC, and a branch model with no operational capability behind any of it. This phase builds the first real one: a bank employee (a teller, at a branch) crediting cash into a customer's BankSphere account. It is also the first time any employee-originated request needs to reach the core banking services (account-service, transaction-service, customer-service) at all — Phase 9A's employee-service never called anything outside itself. Every decision below follows from that: how does an employee-authenticated request reach a system built entirely around customer-authenticated requests, without weakening what already exists for customers, and without turning employee-service into a second banking system.

## Decision 1 — Cash deposit belongs to an employee/operations channel, not a new customer-facing endpoint

A customer can already deposit into their *own* account (`POST /api/v1/accounts/{id}/deposit`, unchanged since Phase 1). A cash deposit is structurally different: the person authorizing it (the employee) is never the account's owner, and the authority to do it comes from a role/permission, not ownership. Reusing the customer deposit endpoint — even with a `customerId` override — was rejected outright: it's exactly the "trust an id from the request body for an access decision" pattern this codebase has never allowed (see `docs/security/authorization.md`), and it would mean a single endpoint's authorization logic has to reason about two entirely different principal types. A separate employee-facing operation, `POST /api/v1/operations/cash-deposits` in employee-service, keeps the two flows — and their two authorization models — structurally apart.

## Decision 2 — employee-service does not own account balances

`Employee`/`Branch`/`CashDepositOperation` are the only tables employee-service owns (see Decision 9). The actual balance mutation happens through a new account-service endpoint, `POST /api/v1/accounts/{id}/employee-deposit` — employee-service calls it, forwarding the acting employee's own bearer token, and never touches `accounts` or any account-service data directly. This is the same "Employee Operations API → Account Service" shape the task's own architecture diagram specified, and it's the same database-per-service boundary every other service in this codebase already respects — cash deposit doesn't get an exception.

## Decision 3 — account-service remains the source of truth

Every fact that matters for the deposit — does the account exist, is it `ACTIVE`, what's its IFSC, what's its current balance, what does optimistic locking do on a concurrent write — is decided inside account-service's own `AccountServiceImpl.employeeDeposit`, using the exact same `Account` entity, the exact same `@Version` column, and (importantly) the exact same `credit()`/`requireActive()` private helpers the existing customer `deposit()` method already uses. This is not a parallel reimplementation of "credit an account" — it's the same one, reached through a second, employee-authorized entry point. A customer's own deposit/withdraw/transfer behavior is completely untouched: not one line of `deposit()`, `withdraw()`, or `transfer()` changed in this phase.

## Decision 4 — transaction-service remains the ledger, and its existing best-effort design is preserved unchanged

The deposit's ledger entry is recorded via the exact same `TransactionClient`/`RestTransactionClient` account-service already uses for every deposit/withdraw/transfer — same interface, same call site shape, same never-rethrows-on-failure contract (ADR-001). The only change to `TransactionClient` is additive: `recordTransaction` now returns `Optional<TransactionRecordResult>` instead of `void`, so a caller that wants the real `TXN-...` reference (this phase's employee-deposit response, which needs to show it) can have it, while every existing caller that doesn't need it is unaffected — they already ignored the return value because there wasn't one. If ledger recording fails, the account balance change is **not** rolled back, exactly as it already wasn't for a customer's own deposit — this phase inherits that trade-off rather than reopening it. `transaction-service`'s own security posture is untouched too: `POST /api/v1/transactions` already required nothing more than "a valid JWT" (never re-verifying identity beyond that — see ADR-001), so letting it also recognize an employee-signed token as "valid" doesn't loosen anything that wasn't already this permissive.

## Decision 5 — no distributed transaction; existing atomicity guarantees are inherited, not re-derived

This phase introduces no new consistency mechanism. The single point of truth for "did the money move" is account-service's own local database transaction around `employeeDeposit` (one `@Transactional` method, one balance write, protected by `@Version` optimistic locking) — identical in shape to every other money-moving operation in this codebase since Phase 1. Ledger recording happens after that transaction has already committed, and is allowed to fail independently (Decision 4). No Kafka, no Outbox, no two-phase commit, no new cross-service saga — explicitly out of scope, per the task's own repeated instruction, and unnecessary: nothing about this operation requires atomicity spanning more than the one database write it actually needs.

`CashDepositOperation` rows (Decision 9) are written to employee-service's own database *after* the account-service call has already succeeded — a failure to write this row does not undo the deposit, and a failure to complete the deposit means no row is written at all (see Decision 9's "only successful operations are persisted" note). This keeps the same pattern already established for ledger recording: the operational record-keeping is secondary to, and never able to invalidate, the actual money movement.

## Decision 6 — branch authorization: derived from `Account.ifsc`, not an invented field

Phase 9A explicitly deferred branch-scoped authorization, noting the branch id flowed through the employee JWT but nothing enforced it. This phase had to actually build that enforcement — and the first real question was whether the domain model could even support it honestly. **Investigated before writing any code**: `Account` (account-service) has no branch reference of any kind and never has since Phase 1; `Customer` (customer-service) has none either. Inventing a new `branch_id` column on `Account` — the naive approach — was rejected: it would mean employee-service's branch concept leaking into account-service's schema for a relationship that already has a real, existing analogue.

`Account.ifsc` (added in Phase 8A, currently a single constant, `BANK0000001`, shared by every account since BankSphere has no branch model on the customer side) and `Branch.ifsc` (added in Phase 9A) are the same kind of value doing the same job real IFSCs do in an actual bank: identifying which branch an account belongs to. The decision: an employee's own branch IFSC is embedded as a new JWT claim (`branchIfsc`, alongside the existing `branchId`), and `AccountServiceImpl.employeeDeposit` compares it against the target account's own `ifsc`. A `TELLER` may only credit an account whose `ifsc` matches their own branch's; a mismatch throws `BranchScopeViolationException` (403). `BRANCH_MANAGER` and `ADMIN` are exempted (`EmployeePrincipal.hasBroadBranchScope()`) — an explicit, documented broader-scope decision, not an oversight, matching the task's own instruction that these two roles "may have broader operational scope, but this must be explicit and documented." (In practice, `ADMIN` doesn't hold `CASH_DEPOSIT` at all per the existing Phase 9A role→permission mapping — see ADR-006 — so this exemption is currently only reachable by `BRANCH_MANAGER`; it's still implemented and tested for `ADMIN` too, since a future permission-mapping change could grant it there without this authorization logic needing to change.)

Since BankSphere currently has exactly one branch and one IFSC, this check is trivially always-true today — but it is a *real* check against a *real* field, not a placeholder, and it becomes meaningfully restrictive the moment a second branch (with its own IFSC) exists, with zero change needed to this code.

## Decision 7 — employee identity source: the verified JWT, never the request body

`CashDepositRequest` has exactly three fields: `accountId`, `amount`, `description`. It has no `employeeId`, no `branchId`, no `customerId` field — Jackson has nothing to bind those to even if a client tried to send them, the same structural (not just conventional) guarantee this codebase already uses elsewhere (see `AccountCreateRequest`'s own precedent). The acting employee's identity comes from `CurrentUser.id(authentication)` in employee-service (the JWT subject, exactly like every other employee-service endpoint since Phase 9A); their branch comes from a fresh `employeeRepository.findById(...)` lookup at request time (not a JWT claim, so it's never stale) for the ledger description, and from the JWT's `branchIfsc` claim (forwarded to account-service) for the actual authorization decision made there. The target account's owning customer is derived entirely server-side, from `accountId`, via account-service's own database — never asserted by the caller anywhere in this flow.

## Decision 8 — customer/account relationship validation: revalidated at the point of mutation, never trusted from an earlier step

The employee portal's search step (`GET /api/v1/operations/customer-search`) tells the browser which accounts belong to which customer, so the UI can render "Select Account." That response is **not** trusted as authorization for the deposit that follows — `CashDepositRequest` doesn't even carry a `customerId` for the deposit call to check it against. The actual mutation (`AccountServiceImpl.employeeDeposit`) independently looks up the account fresh, from `accountId` alone, and makes its own `ACTIVE`/branch-scope decisions at that moment — closing the TOCTOU gap a naive "trust what the search step already told you" design would have left open (an account closed or reassigned between search and submit is caught for real, not assumed away).

## Decision 9 — audit and operational history: structured logs (Phase 9A's pattern, extended) plus one minimal, carefully-scoped table

Every cash deposit produces three possible structured audit lines — `CASH_DEPOSIT_STARTED`, `CASH_DEPOSIT_SUCCEEDED`, `CASH_DEPOSIT_FAILED` — via the same `EmployeeAuditLog`/`com.banksphere.employee.AUDIT` logger Phase 9A established, extended (not replaced) with deposit-specific fields (`branchId`, `accountId`, `amount`). This is explicitly not the real Audit Service (no Kafka, no new database beyond what's described next) — see ADR-006, Decision 7, unchanged in kind.

The task also explicitly asked for a simple, real "employee operations history" screen, with an equally explicit escape valve: *"if persistent operational history requires a new domain/service that would exceed this phase, document it rather than creating an inappropriate table inside employee-service."* The judgment call made here: a **minimal** table, `cash_deposit_operations`, was implemented rather than skipped, because it could be built cleanly within the existing employee-service boundary without turning it into a second banking database. What it stores is deliberately limited to immutable, point-in-time operational facts captured at the moment of the deposit — `operationReference`, `employeeId`/`employeeNumber`, `branchId`/`branchCode`, `customerId`, `accountId`/`accountNumber`, `amount`/`currency`, `status`, and the real `transactionReference` (nullable). It never stores anything mutable that could drift out of sync with its owning service — no balance, no account status, no customer name. The one genuinely "customer data"–shaped field a nice history UI wants (the customer's display name) is deliberately **not stored** — `OperationsServiceImpl.cashDepositHistory` resolves it live, per request, via the same `CustomerLookupClient` the search step uses, tolerating a per-row failure (shown as `null`/blank rather than fabricated) rather than ever risking a stale or duplicated name at rest. Only **successful** deposits are persisted (see Decision 5) — a failed attempt is fully captured in the audit log alone, since account-service's rejection may occur before any verified account/customer identifiers exist to safely record.

## Decision 10 — future ATM reuse

Nothing about `AccountServiceImpl.employeeDeposit` or the branch-scope check is teller-specific in its actual mechanics — it's "an authenticated principal, holding a specific permission, associated with a branch IFSC, crediting a specific account." A future ATM/self-service cash-deposit channel would authenticate differently (a card+PIN or similar, not an employee JWT) but could, in principle, reach the *same* account-service endpoint and the *same* balance-mutation code path, once ATM identity has its own principal type — exactly the same "second principal type, same underlying operation" shape this phase already established for employees on top of the customer-only foundation. This is recorded as a plausible future direction, not a commitment — no ATM work is started in this phase.

## Consequences

- Three services beyond employee-service (`account-service`, `transaction-service`, `customer-service`) now accept a second, structurally distinct token type in addition to customer JWTs, each via its own `EmployeeJwtValidator`/`EmployeeJwtAuthenticationFilter` pair, added alongside (never replacing) the existing customer-token filter. Every existing customer-facing endpoint's code is byte-for-byte unchanged.
- A real, if currently trivial (single-branch), branch-scoped authorization boundary now exists and is enforced server-side, using a field (`Account.ifsc`) that already existed for an unrelated reason (Phase 8A) rather than a newly invented one.
- `employee-service` gained its first table that stores anything beyond employee/branch identity (`cash_deposit_operations`) — deliberately scoped to avoid becoming a second source of truth for banking data (see Decision 9).

## A known, accepted rough edge

An employee token that reaches one of the *existing*, unmodified customer-only endpoints (e.g. `GET /api/v1/customers/{id}`) doesn't fail cleanly with a 403 — `CurrentUser.id(authentication)` tries `UUID.fromString()` on the non-UUID-shaped `EmployeePrincipal`/`EmployeeIdentity` and throws `IllegalArgumentException`, which each service's existing generic handler turns into a `400`. No data is ever leaked (the failure happens before any lookup), but the status code is not as clean as a dedicated check would produce. Fixing this properly would mean auditing every existing endpoint to explicitly reject a wrong-principal-type `Authentication` — real work, deliberately not undertaken this phase since it touches code outside cash deposit's own scope. Recorded here rather than silently left undiscovered; a regression test (`CustomerControllerTest.getCustomer_isRejected_whenCallerIsAnEmployeeToken_notMisreadAsACustomerId`) pins the current (imperfect but safe) behavior.

## Deferred to a later phase

KYC, loans, cards, cash withdrawal by an employee (only deposit was in scope), an ATM channel, Kafka/Outbox, a real Audit Service, database-backed branch-scope rules beyond the IFSC comparison, multi-branch support (a second seeded branch with a distinct IFSC would make Decision 6's check meaningfully restrictive today — not built, since nothing in this phase needed a second branch to exist) — all explicitly out of scope per the task's own repeated instruction.
