# Microservices

_Status: Phase 6 (Microservices) in progress — `beneficiary-service` implemented, Phase 7A added an internal transfer capability to the existing `account-service`, Phase 9A added `employee-service` (a new service outside the original Phase 6 list, backing a second (employee) channel rather than a new customer-facing capability), Phase 9B connected that channel to the core banking services for the first time (branch cash deposit), Phase 9C added a sixth service, `kyc-service`, plus a Customer 360 aggregation in `employee-service`, and Phase 9D added OTP login, refresh tokens, and step-up authentication to `customer-service`, plus a step-up/idempotency gate to `account-service`'s existing transfer endpoint. The rest of this document remains a placeholder for the other originally-listed services (api-gateway, auth-service, payment-service, card-service, loan-service, notification-service, audit-service) until each is built._

See [`backend/README.md`](../../backend/README.md) for the current service list and responsibilities.

## `account-service` — `http://localhost:8082` (Phase 7A addition; Phase 9B employee endpoints; Phase 9D step-up + idempotency)

**Responsibility and bounded context:** owns account records, balances, and — as of Phase 7A — atomic internal account-to-account transfers (`POST /api/v1/accounts/transfer`), in addition to its existing create/deposit/withdraw responsibility. As of Phase 9B, also the sole place a branch employee's cash deposit actually mutates a balance (`POST /api/v1/accounts/{id}/employee-deposit`) — reusing the exact same balance-mutation code path as a customer's own deposit, not a parallel implementation. As of Phase 9D, `transfer()`'s existing validation/mutation logic is unchanged but now gated by `StepUpPolicy` (a transfer at/above a configurable threshold requires a verified step-up challenge, confirmed with customer-service before any balance mutation) and wrapped with an optional client-supplied `idempotencyKey` (enforced by a real database unique constraint, not just an application-layer check) so a double-click/retry can never execute the same transfer twice. Does **not** talk to a payment switch, interbank rails, or any external bank — see [ADR-004](decisions/ADR-004-internal-account-transfer.md) for the transfer design, [ADR-007](decisions/ADR-007-branch-cash-deposit.md) for the cash-deposit design, and [ADR-009](decisions/ADR-009-customer-otp-and-step-up-authentication.md) for the step-up/idempotency design — all three documenting what's deliberately deferred (a separate Transfer Service, Kafka, Outbox).

**Exposed REST endpoints (transfer/employee-relevant):** `POST /api/v1/accounts/transfer` (now accepts optional `stepUpChallengeId`/`idempotencyKey`); `GET /api/v1/accounts/employee-lookup[/customer/{customerId}]`, `POST /api/v1/accounts/{id}/employee-deposit` (Phase 9B, employee-token-only) — see [docs/api/README.md](../api/README.md) for full request/response detail.

**Kafka topics produced/consumed:** none — deferred, see [scope.md](../00-project-overview/scope.md).

**Dependencies on other services:** transaction-service, exactly as deposit/withdraw already did (best-effort ledger recording via `TransactionClient`, forwarding the caller's own JWT — a customer's for a customer deposit, an employee's for a cash deposit) — the integration itself is unchanged since Phase 7A. See [ADR-004, Decision 5](decisions/ADR-004-internal-account-transfer.md#decision-5--ledger-recording-stays-best-effort-exactly-like-adr-001). As of Phase 9B, also independently validates employee-service-issued JWTs (own `EmployeeJwtValidator`, `EMPLOYEE_JWT_SECRET`) for the three employee-only endpoints above — see [ADR-007](decisions/ADR-007-branch-cash-deposit.md). As of Phase 9D, also calls **into** customer-service (`StepUpVerificationClient`, forwarding the customer's own bearer token, never a shared secret) to confirm a step-up challenge before a gated transfer executes — this call must propagate failure, unlike the best-effort `TransactionClient` pattern above.

## `beneficiary-service` — `http://localhost:8084`

**Responsibility and bounded context:** manages the beneficiaries a customer can use for a future money transfer — adding, listing, updating display fields, and deactivating them. Does **not** move money, initiate a transfer, or talk to any payment rail — see [ADR-003](decisions/ADR-003-beneficiary-service.md) for the full reasoning and what's deliberately deferred.

**Owned data/schema:** `banksphere_beneficiary` database, `beneficiaries` table — see [docs/database/README.md](../database/README.md#banksphere_beneficiary-beneficiary-service).

**Exposed REST endpoints:** `POST/GET /api/v1/beneficiaries`, `GET/PUT/DELETE /api/v1/beneficiaries/{id}` — see [docs/api/README.md](../api/README.md#beneficiary-service--httplocalhost8084) for full request/response detail.

**Kafka topics produced/consumed:** none — Kafka is out of scope until its own phase (see [scope.md](../00-project-overview/scope.md)).

**Dependencies on other services:** none outbound in this phase (see [ADR-003, Decision 5](decisions/ADR-003-beneficiary-service.md#decision-5--no-outbound-calls-to-other-services-yet)). Inbound: validates JWTs issued by customer-service (shared `JWT_SECRET`, same stateless-verification pattern as account-service/transaction-service — see [docs/security/jwt.md](../security/jwt.md)). As of Phase 9C, also independently validates employee-service-issued JWTs (own `EmployeeJwtValidator`, `EMPLOYEE_JWT_SECRET`) for one new employee-only endpoint, `GET /api/v1/beneficiaries/employee/customer/{customerId}` (`CUSTOMER_VIEW`), feeding the Customer 360 aggregation — this service's first-ever acceptance of an employee token. A future Transfer/Payment Service is expected to call *into* this service to confirm a beneficiary exists, is `ACTIVE`, and is owned by the initiating customer before starting a transfer.

## `kyc-service` — `http://localhost:8086` (Phase 9C)

**Responsibility and bounded context:** owns KYC applications, document metadata, document verification state, and review decisions — the sixth independent BankSphere service, and the first to expose a complete API surface directly to *both* portals (not proxied through employee-service). Does **not** own customer accounts, the transaction ledger, or employee identity — see [ADR-008](decisions/ADR-008-kyc-domain-and-document-storage.md).

**Owned data/schema:** `banksphere_kyc` database, `kyc_applications`/`kyc_documents`/`kyc_status_history` tables — see [docs/database/README.md](../database/README.md#banksphere_kyc-kyc-service).

**Exposed REST endpoints:** customer-facing `POST /api/v1/kyc/applications`, `GET /api/v1/kyc/applications/me`, `GET /api/v1/kyc/applications/{id}`, `POST /api/v1/kyc/applications/{id}/documents`, `POST /api/v1/kyc/applications/{id}/submit`, `POST /api/v1/kyc/applications/{id}/resubmit`; employee-facing `GET /api/v1/kyc/employee/queue`, `GET /api/v1/kyc/employee/applications/{id}`, `GET /api/v1/kyc/employee/customer/{customerId}`, `POST /api/v1/kyc/employee/applications/{id}/start-review`, `POST /api/v1/kyc/employee/documents/{id}/verify`, `POST /api/v1/kyc/employee/documents/{id}/reject`, `GET /api/v1/kyc/employee/documents/{id}/content`, `POST /api/v1/kyc/employee/applications/{id}/request-information`, `POST /api/v1/kyc/employee/applications/{id}/approve`, `POST /api/v1/kyc/employee/applications/{id}/reject` — see [docs/api/README.md](../api/README.md) and [docs/architecture/customer-360-and-kyc.md](customer-360-and-kyc.md).

**Kafka topics produced/consumed:** none — deferred, see [scope.md](../00-project-overview/scope.md).

**Dependencies on other services:** none outbound. Inbound: validates both customer-service-issued JWTs (`JWT_SECRET`) and employee-service-issued JWTs (`EMPLOYEE_JWT_SECRET`) — the first service with a genuinely dual-principal-type API surface, not just "also accept an employee token on an existing customer endpoint." Document bytes are stored via a `DocumentStorage` interface (`LocalDocumentStorage` today, filesystem-backed — no AWS/S3 dependency yet). See [customer-360-and-kyc.md](customer-360-and-kyc.md).

## `employee-service` — `http://localhost:8085` (Phase 9A identity/RBAC; Phase 9B operations)

**Responsibility and bounded context:** owns employee identity and authorization metadata (employees, branches, role assignment) for BankSphere's second, internal-only channel — the employee/bank-operations portal — plus, as of Phase 9B, a minimal operational log of cash deposits it has orchestrated (`cash_deposit_operations` — immutable point-in-time facts only, never a mutable copy of balance/customer data). Does **not** own or duplicate any customer/account/transaction data, does **not** yet expose most operational capability (KYC, loans, cards — only cash deposit exists so far), and does **not** share a JWT signing key, session, or frontend with the customer-facing services — see [ADR-006](decisions/ADR-006-employee-identity-and-rbac.md) and [ADR-007](decisions/ADR-007-branch-cash-deposit.md) for the full reasoning, and [docs/architecture/employee-platform.md](employee-platform.md) / [employee-operations.md](employee-operations.md) for the complete design.

**Owned data/schema:** `banksphere_employee` database, `branches`/`employees`/`employee_roles`/`cash_deposit_operations` tables — see [docs/database/README.md](../database/README.md).

**Exposed REST endpoints:** `POST /api/v1/employees/auth/login`, `GET /api/v1/employees/me`, `POST/GET /api/v1/employees`, `GET/PUT /api/v1/employees/{id}[/status]`; as of Phase 9B, the "Employee Operations API": `GET /api/v1/operations/customer-search`, `POST /api/v1/operations/cash-deposits`, `GET /api/v1/operations/cash-deposits/history` — see [docs/architecture/employee-platform.md](employee-platform.md) / [employee-operations.md](employee-operations.md) for the full authentication/authorization model.

**Kafka topics produced/consumed:** none — Kafka is out of scope until its own phase (see [scope.md](../00-project-overview/scope.md)).

**Dependencies on other services:** none in Phase 9A. As of Phase 9B: **account-service** (customer/account lookups, the actual cash-deposit balance mutation) and **customer-service** (customer name lookups) — both called server-to-server from `OperationsServiceImpl`, forwarding the acting employee's own bearer token so each downstream service independently re-verifies it, exactly the same "forward the caller's real token" pattern account-service already used calling transaction-service since Phase 1. Employee tokens are still signed and validated with employee-service's own key (`EMPLOYEE_JWT_SECRET`), independent of customer-service's `JWT_SECRET` — account-service/transaction-service/customer-service each gained their own `EmployeeJwtValidator` to recognize it, but none of them can issue one (only employee-service does) — see [ADR-006, Decision 2](decisions/ADR-006-employee-identity-and-rbac.md#decision-2--employee-jwts-are-signed-with-a-separate-key-from-customer-jwts-not-just-a-separate-claim) and [ADR-007](decisions/ADR-007-branch-cash-deposit.md).
