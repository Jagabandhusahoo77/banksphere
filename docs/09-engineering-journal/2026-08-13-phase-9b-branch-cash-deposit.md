# 2026-08-13 — Phase 9B: Branch Cash Deposit

## Objective

Build the first real employee-initiated banking operation on top of Phase 9A's identity/RBAC foundation: a bank employee crediting cash into a customer's account, end to end — real balance mutation, real ledger entry, immediately visible through the existing customer portal, with real server-side branch authorization. Explicitly not KYC, loans, cards, ATM, Kafka, or anything beyond cash deposit.

## Inspection before writing code

Per the task's own explicit instruction, the existing domain model was inspected before any design decision was made — particularly whether `Account` or `Customer` had any existing branch relationship. Neither did: `Account` has never had a branch field, and `Customer` has none either. This ruled out the naive approach (inventing a `branch_id` column on `Account`) and led directly to the actual design: `Account.ifsc` (Phase 8A) and `Branch.ifsc` (Phase 9A) already encode the same relationship a real IFSC encodes in an actual bank — comparing them is real branch scoping, not a placeholder, using a field that already existed for an unrelated reason.

Also inspected before assuming anything: the actual `RolePermissions` mapping (confirmed `CASH_DEPOSIT` is held only by `TELLER` and `BRANCH_MANAGER`, not `ADMIN` — matching the task's own "inspect rather than assume" instruction about `OPERATIONS`/`ADMIN`), account-service's existing deposit/withdraw code (to reuse its `credit()`/`requireActive()` helpers rather than reimplementing them), and transaction-service's `POST /api/v1/transactions` (discovering it already required nothing beyond "a valid JWT" — the ideal, already-permissive endpoint to extend for employee tokens with zero other change).

## The central architectural question: how does an employee-authenticated request reach account-service?

Phase 9A's employee-service never called any other service. This phase's first real design fork: should account-service/transaction-service/customer-service learn to validate employee-signed JWTs directly (a second `EmployeeJwtValidator` per service, mirroring the existing customer-token pattern), or should employee-service call them via a shared internal secret, asserting the employee's already-verified identity in headers?

The shared-secret design was considered — smaller blast radius, less new code — but rejected: it's exactly the "trust an asserted identity rather than re-deriving it from a verified token" pattern this codebase's own permanent rules (`docs/security/authorization.md`, CLAUDE.md) have never allowed anywhere else. The chosen design instead replicates the *already-established* "downstream service independently re-verifies the caller's real token" pattern (the one account-service has used calling transaction-service since Phase 1) for a second principal type: each of the three services gained its own `EmployeeJwtValidator`/`EmployeeJwtAuthenticationFilter` pair, using the same `EMPLOYEE_JWT_SECRET` employee-service itself signs with, running *alongside* — via explicit filter ordering, never replacing — the existing, byte-for-byte-unchanged customer-token filter. Since a token can only ever verify against one of two cryptographically distinct keys, there's no ambiguity about which principal type ends up authenticated.

## Branch scoping: real, but currently trivial

A `TELLER`'s employee JWT now carries a `branchIfsc` claim (added alongside the existing `branchId` claim from Phase 9A). `AccountServiceImpl.employeeDeposit` compares it against the target account's own `ifsc` and rejects a mismatch with `403` (`BranchScopeViolationException`) — unless the employee holds `BRANCH_MANAGER` or `ADMIN` (`EmployeePrincipal.hasBroadBranchScope()`), an explicit, documented exemption per the task's own instruction that these roles "may have broader operational scope, but this must be explicit and documented." Since BankSphere currently has exactly one seeded branch/IFSC, this check is trivially satisfied by every real request today — but it's a genuine comparison against a real field, not a stub, and needs zero code changes to become meaningfully restrictive the moment a second branch exists.

## Design: keeping the actual balance mutation code path singular

`AccountServiceImpl.employeeDeposit` was written to call the *same* private `credit()`/`requireActive()` helpers `deposit()` already used — not a parallel "employee version" of crediting an account. The only genuinely new logic is the branch-scope check and the different (permission-based, not ownership-based) authorization gate in front of it. This was a deliberate choice to avoid the two code paths ever silently drifting apart in how they handle money.

## Extending `TransactionClient` without breaking anything

The task's UI mock wanted a real `TXN-...` reference shown to the employee on success — but `TransactionClient.recordTransaction` was `void`, since no existing caller needed the response body (`RestTransactionClient` called `.toBodilessEntity()`). Changed the interface to return `Optional<TransactionRecordResult>` (a small new partial-mapping DTO, `{ id, transactionReference }`) — purely additive: every existing call site (`deposit`, `withdraw`, `transfer`) already discarded the return value as a bare statement, so Java accepted the new non-void return type with zero code changes needed at those call sites, confirmed by a clean `test-compile` on the first attempt.

## Tests written to prove the security properties, not just the happy path

Beyond the standard success/not-found/not-active/amount-validation coverage, three tests specifically prove the properties this phase's task cared most about:
- `AccountServiceImplTest.employeeDeposit_neverTakesEmployeeIdentityFromTheAmountRequest_onlyFromTheAuthenticatedPrincipal` — a regression-proofing test making explicit that `AmountRequest` has no identity fields at all.
- `AccountControllerTest`'s parameterized `employeeDeposit_returns403_forRolesWithoutCashDeposit` — authenticates as every one of `KYC_OFFICER`/`LOAN_OFFICER`/`CARD_OFFICER`/`OPERATIONS`/`ADMIN` in turn and confirms each is rejected, pinned against the real `RolePermissions` table rather than a hand-maintained duplicate of it.
- `CustomerControllerTest.getCustomer_isRejected_whenCallerIsAnEmployeeToken_notMisreadAsACustomerId` — a documented regression test for the one known rough edge (see below), proving it fails safely even though it doesn't fail *cleanly*.

## A documented, accepted rough edge (not silently discovered and ignored)

An employee token that reaches an *existing*, unmodified customer-only endpoint (e.g. `GET /api/v1/customers/{id}`) doesn't get a clean `403` — `CurrentUser.id(authentication)` tries `UUID.fromString()` on the non-UUID-shaped employee principal and throws `IllegalArgumentException`, which each service's pre-existing generic handler turns into a `400`. No data is ever leaked (the failure happens before any lookup runs), but the status code isn't as clean as a dedicated check would produce. Fixing this properly means auditing every existing customer-only endpoint across three services to explicitly reject a wrong-principal-type `Authentication` — real work outside cash deposit's own scope, so it was documented (ADR-007) and pinned with a regression test rather than either silently left undiscovered or scope-creeped into a fix.

## Employee operations history: a real, minimal, carefully-scoped table

The task's own instructions offered an explicit escape valve for this feature ("if persistent operational history requires a new domain/service that would exceed this phase, document it rather than creating an inappropriate table"). The judgment call: build it, but keep employee-service's new `cash_deposit_operations` table strictly to immutable, point-in-time operational facts (which account, how much, by whom, when, the real transaction reference) — never mutable state like balance or a customer's display name, both of which are resolved live from their owning service on every read of the history endpoint instead, tolerating a per-row lookup failure (rendered as `null`) rather than ever risking a stale or duplicated value at rest. Only successful deposits are persisted — a failed attempt has no verified account/customer identifiers safe to record, and is fully captured in the structured audit log alone.

**employee-service** (+26 tests, 83 total): `OperationsServiceImplTest` (customer search by both identifiers, the "provide exactly one" validation, cash deposit success/description-building/downstream-failure-handling, history with live name resolution and graceful per-row failure), `OperationsControllerTest` (the same real-mapping-pinned parameterized RBAC test as account-service, applied to the employee-service side of the same operation, plus malformed-request/history/search coverage), and an extended `JwtServiceTest` asserting the new `branchIfsc` claim round-trips correctly.

**employee-portal** (+9 tests, 24 total): the full search → select → amount → review → confirm → success wizard flow with real mocked service responses, a friendly-404 test, a branch-scope-violation friendly-error test, a double-submission-prevention test, and a Search-button-disabled-until-valid-input test — plus history-page tests for real data rendering, a null-customer-name placeholder (never fabricated), an empty state, and an error state.

## Real end-to-end verification

**HTTP-level** (`curl`, against the actual rebuilt Docker images on the live shared Postgres): registered a real customer, opened a real ₹20,000 account, logged in as the real seeded teller (`jane.teller`, carrying the new `branchIfsc` claim), searched for the customer by account number, performed a real ₹10,000 cash deposit, and — critically — verified the result via the *customer's own* authenticated calls to account-service and transaction-service (exactly what the customer portal itself calls, not a special verification endpoint): balance `30000.00`, a real `DEPOSIT` transaction with the correct `CASH DEPOSIT - Branch HQ001 (customer requested)` description and the matching `TXN-...` reference. Separately proved: a KYC officer's real cash-deposit attempt returns `403`; a customer JWT presented to employee-service's operations endpoint returns `401` (unauthenticated, wrong key entirely); the *same* customer JWT presented directly to account-service's `employee-deposit` endpoint returns `403` (authenticated as a customer, just lacking the `CASH_DEPOSIT` authority) — the correct 401-vs-403 distinction, not a coincidence. Confirmed the structured `CASH_DEPOSIT_STARTED`/`SUCCEEDED` audit lines in employee-service's own logs, with a real correlation id.

**Browser-level** (Puppeteer against the actual system Chrome, driving the actual compiled portals): a real employee session walked the full 5-step Cash Deposit wizard for a fresh customer end to end, landing on a success screen with a real `CD-...` operation reference and `TXN-...` transaction reference and the correct new balance. A second, independent browser tab then logged into the actual compiled *customer portal* as that same customer and confirmed the updated balance on the Accounts page and a `DEPOSIT` transaction with the correct `+₹10,000.00` amount and `CASH DEPOSIT` description on the Transactions page — using the customer portal's own existing, completely unmodified code. Returning to the employee portal, the Cash Deposit History page showed the same real operation reference against the real customer name, resolved live. **22/22 checks passed, zero console or page errors on either portal.**

## What was deliberately not done

Cash withdrawal by an employee (only deposit was in scope), KYC, loans, cards, an ATM channel, Kafka, Outbox, a real Audit Service, Kubernetes, external transfers/UPI/IMPS/NEFT, a second seeded branch (would make the now-real branch-scope check meaningfully restrictive, but wasn't needed to prove the check itself works — see the unit/controller tests, which construct a mismatched-branch scenario directly), a database-backed role/permission admin UI, and a proper fix for the documented employee-token-on-customer-endpoint rough edge — all explicitly out of scope per the task's own repeated instruction, or explicitly deferred and documented (ADR-007) rather than silently skipped.
