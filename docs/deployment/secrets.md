# Secrets (AWS DEV/TEST, Phase 10A)

## Decision: AWS Systems Manager Parameter Store (SecureString), not Secrets Manager

Both were on the table (the task explicitly allowed either). Chosen: **SSM Parameter Store**, SecureString tier, encrypted with the AWS-managed `alias/aws/ssm` KMS key (no customer-managed key — see the cost note below).

**Why:** for this phase's actual requirement (store a handful of static values per environment — `DB_PASSWORD`, `JWT_SECRET`, `EMPLOYEE_JWT_SECRET` — and let one EC2 instance read them), SSM Parameter Store's Standard tier is **free** (no per-secret monthly charge, no API-call charge for `GetParameter` at this volume), while Secrets Manager charges ~$0.40/secret/month plus API-call pricing. Secrets Manager's real advantage — automatic rotation with Lambda — is not a requirement this phase (these values do not need to rotate on a schedule yet), so its cost is not currently buying anything DEV/TEST needs. Revisit for PROD, where rotation becomes a real requirement — see `infrastructure/terraform/environments/prod/README.md`.

## What's stored, and where

Each environment's secrets live under its own SSM path prefix — `/banksphere/dev/*` or `/banksphere/test/*` — created by `infrastructure/terraform/environments/<env>/secrets.tf`:

| Parameter | Type | Generated by |
|---|---|---|
| `/banksphere/<env>/DB_PASSWORD` | SecureString | Terraform (`random_password`, 32 chars) |
| `/banksphere/<env>/JWT_SECRET` | SecureString | Terraform (`random_password`, 64 chars — well over the ≥32-byte HS256 minimum, see `docs/security/jwt.md`) |
| `/banksphere/<env>/EMPLOYEE_JWT_SECRET` | SecureString | Terraform (`random_password`, 64 chars) |
| `/banksphere/<env>/DOMAIN_NAME` | String (not secret) | Terraform, only if `domain_name` is set |

None of these values are ever typed by a human, committed to git, or baked into a Docker image. **Post-rework**: they are fetched **once**, at node bootstrap (not on every deploy — see below), by `infrastructure/terraform/modules/k3s`'s bootstrap script, via the instance's own IAM role, and written directly into a Kubernetes `Secret` (`banksphere-app-secrets`, in the environment's namespace) — never to a file on the instance's own disk. The Helm chart's Pod specs reference this Secret's keys via `secretKeyRef` (see `docs/deployment/helm.md`); the chart itself never creates or modifies the Secret. `infrastructure/scripts/<env>/deploy.sh` (the original Docker-Compose-era `.env`-writing script) is retained only as a **reference/local-fallback artifact** — see `infrastructure/docker/README.md` — it is not part of the cloud deploy path anymore.

**Why once, not per-deploy**: unlike the original Docker-Compose design (which re-read `.env` on every `deploy.sh` run), these values don't change on their own — Terraform generates them once, and the bootstrap script provisions the Secret once, at first boot. A subsequent deploy (a new image tag reaching the environment via the GitOps commit → Argo CD reconcile flow — see `docs/deployment/gitops.md`) never touches SSM or this Secret again; it only changes `image.tag` in `values-<env>.yaml`.

## IAM scoping — the actual enforcement of "DEV and TEST must not share secrets"

DEV's EC2 instance role can `ssm:GetParameter(s)` only under `/banksphere/dev/*`; TEST's role only under `/banksphere/test/*` (see `infrastructure/terraform/modules/ec2`'s `aws_iam_role_policy.app_access`, `Sid = "ReadOwnEnvironmentSecrets"`). This is enforced by IAM, not by convention or by which value happens to be written where — a compromised DEV instance cannot use its own role to read TEST's database password.

## Known trade-off: these values also live in Terraform state

Terraform must know a `random_password` resource's actual value to manage it, so it appears in `terraform.tfstate`. With **local state** (this phase's current setup — see `infrastructure/README.md`'s "before you apply" checklist), that state file **is** the real secret store today. This is called out explicitly rather than glossed over: before any real or shared use, move to a remote backend (S3, versioned, SSE-KMS encrypted, public access blocked, plus a DynamoDB table for locking) so the state itself is encrypted at rest and access-controlled — local state on a laptop or CI runner's disk is not an acceptable long-term home for it.

## What's still NOT wired to anything

- **OTP secrets** — there aren't any to store; the OTP domain doesn't carry a static secret (see ADR-009), only per-request generated codes, hashed and stored in Postgres, not SSM.
- **Entra ID client secret** — Entra SSO is explicitly not implemented this phase (see the task's own scope boundary). Once it is, its client secret belongs in this same SSM path (`/banksphere/<env>/ENTRA_CLIENT_SECRET`), read the same way.
- **API keys for a real SMS/Email/WhatsApp OTP provider** — also not implemented yet (see ADR-009's future-providers section); same placement once one exists.
