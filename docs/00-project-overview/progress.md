## What was built in Phase 7A — atomic internal account transfer (2026-08-13)

See the [Phase 7A engineering journal entry](../09-engineering-journal/) and [ADR-004](../architecture/decisions/ADR-004-internal-account-transfer.md) for full detail:

- `POST /api/v1/accounts/transfer` in `account-service` — one `@Transactional` method (not two independent REST calls, not a new microservice) moves money between two accounts atomically within account-service's own database. Source ownership is enforced from the JWT exactly like every other account-service endpoint; the destination account may belong to any customer.
- Deterministic account ordering (ascending `UUID.compareTo()`, independent of source/destination role) plus `saveAndFlush` (not `save`) to pin the actual database write order, avoiding the classic opposite-direction deadlock shape between two concurrent transfers — without introducing pessimistic locking, which nothing else in this codebase uses. The existing `Account.version` optimistic-locking column remains the sole mechanism that rejects a lost update.
- Two new real-PostgreSQL integration tests (`AccountTransferRollbackIT`, `AccountTransferConcurrencyIT`), run via a newly added `maven-failsafe-plugin` binding during `mvn verify` — Mockito unit tests alone can't prove a real database transaction rolled back. The rollback test manufactures a genuine mid-transaction Postgres row-lock conflict from a second JDBC connection (no test-only hook added to production code) and proves both balances are unchanged afterward; the concurrency test proves that of two simultaneous conflicting transfers, exactly one succeeds and the balance never goes negative.
- `deposit()`/`withdraw()` were refactored to share `credit()`/`debit()`/`requireSufficientBalance()` helpers with the new `transfer()` method, removing duplicated arithmetic — their external behavior and all 42 existing/extended unit + controller tests are unchanged.
- `TRANSFER`-type ledger legs recorded in transaction-service on the same best-effort, never-rethrows basis deposit/withdraw already use (ADR-001) — verified live, including a run where transaction-service was genuinely unreachable and the transfer still completed successfully.
- Live end-to-end smoke test against the real running Docker stack: registered two customers, opened two accounts, and exercised every documented status code (200/400/401/403/404/422) for the new endpoint, then confirmed the resulting `TRANSFER` ledger row in transaction-service via its own API.

## What was built in Phase 8A — account identity (IFSC) + deposit workflow fix (2026-08-13)

See the [Phase 8A engineering journal entry](../09-engineering-journal/) for full detail:

- **Deposit was never actually broken.** A real-browser diagnostic (Puppeteer driving actual Chrome against the live Docker stack — the first time this project had real browser tooling available, not just `curl`/static analysis) traced the entire deposit request end-to-end against an existing account and found a clean `200` at every hop: correct URL/method/body/headers, a successful CORS preflight, correct balance update, correct ledger entry, correct frontend refresh. The real root cause was upstream: **there was no way to open an account through the portal at all** — `accountService.createAccount()` existed but had zero UI callers (a known, previously-documented Phase 1/2 gap) — so a real user could never reach a working deposit form via the natural registration → open account → deposit journey.

- Added `Account.ifsc` end-to-end: entity, `V2__add_ifsc_to_accounts.sql` (nullable → backfilled → `NOT NULL` + format `CHECK`, safe against existing rows), `AccountResponse`, frontend type/display. Server-controlled single constant (`BANK0000001`) — BankSphere has no branch model, so IFSC identifies the bank, not the account, and is never randomized or client-suppliable.
- `AccountDetails.tsx` redesigned its identity section: "BankSphere" + full copyable Account Number + IFSC + Account Type + Available Balance + Status.
- Fixed a real, separate pre-existing bug found along the way: the frontend's `AccountCreateRequest` type still had a stale `customerId` field left over from before Phase 3A removed it from the backend contract.
- 6 new backend tests (server-generated 12-digit account number, retried on collision, single constant IFSC, client can't smuggle in `accountNumber`/`ifsc`/`customerId`) + 7 new/updated frontend tests (account creation payload correctness, IFSC/account-number display, 403/500 friendly error mapping) — 48 backend tests and 34 frontend tests passing overall.
- **Migration safety proven live, not just by reading the SQL**: `V2` was applied to the actual shared `banksphere-postgres` database, which already held 33 real account rows from every prior phase's testing — confirmed after migration that all 33 were correctly backfilled to `BANK0000001` with zero `NULL`s.
- **Real end-to-end browser verification**: a fresh customer registered, logged in, opened a Savings account, and deposited ₹10,000 — all 13 steps of this phase's own test scenario passed driving the actual compiled portal UI in headless Chrome, with zero non-2xx responses and zero console/page errors across 16 real HTTP requests.

## What was built in Phase 8B — recipient resolution and transfer UX (2026-08-13)

See the [Phase 8B engineering journal entry](../09-engineering-journal/) and [ADR-005](../architecture/decisions/ADR-005-recipient-resolution.md) for full detail:

- **Closed the exact gap Phase 8 discovered and documented**: `POST /api/v1/accounts/transfer`'s destination is no longer an internal `destinationAccountId` UUID — it's `destinationAccountNumber` + `destinationIfsc`, resolved server-side via a new shared `resolveDestinationAccount()` helper in `AccountServiceImpl`. The internal account id is now never present in the transfer API, request or response, in either direction.
- New `POST /api/v1/accounts/resolve-recipient` endpoint (`ResolveRecipientRequest{accountNumber, ifsc}` → `ResolveRecipientResponse{accountNumber, ifsc, bankName}`) lets the frontend verify a recipient before committing, matching real bank "verify payee" UX. Deliberately minimal response — no id, no `customerId`, no balance — keeps this from becoming a meaningful account-enumeration tool; full reasoning in ADR-005.
- IFSC checked before any database lookup: a non-`BANK0000001` IFSC fails fast with a distinct `422` (`UnsupportedIfscException`), separate from a `404` (`RecipientNotFoundException`) for a correctly-formatted but nonexistent BankSphere account number.
- Transfer page's recipient step rebuilt around three tabs — **My accounts** (resolved locally, no API call), **Saved beneficiary** (only `ACTIVE` beneficiaries listed; selecting one re-verifies against `resolve-recipient` rather than trusting the saved snapshot), **Account number** (manual entry + an explicit "Verify recipient" step) — replacing the Phase 8 "paste the recipient's raw Account ID" stopgap entirely. A recipient preview card shows a masked account number, IFSC, and bank name once resolved; no fabricated name is shown for manually-entered recipients (only saved-beneficiary/own-account selections have a real name source).
- Default per-leg ledger descriptions changed from `"Transfer to account " + destination.getId()` (an opaque UUID) to `"Transfer to account " + destination.getAccountNumber()` — a real customer reading their own transaction history now sees something recognizable.
- No database migration needed — this phase is pure query/API-contract logic on top of Phase 8A's already-backfilled `ifsc` column.
- Backend: `AccountRepository.findByAccountNumber`, 2 new exceptions, rewritten `TransferRequest`/`TransferResponse` DTOs, new `ResolveRecipientRequest`/`ResolveRecipientResponse` DTOs, rewritten `transfer()` + new `resolveRecipient()` in `AccountServiceImpl`, both real-Postgres integration tests updated to generate valid 12-digit account numbers. 64 tests total (28 controller + 34 service + 2 IT), `mvn clean verify` clean.
- Frontend: `types/account.ts`, `accountService.ts` (`resolveRecipient`), full `Transfer.tsx` rewrite, `Transfer.test.tsx` rewritten (8 tests covering resolution, friendly 404 handling, beneficiary auto-resolution, submitting the account number never the UUID, double-submit prevention, honest rejection display). 37 frontend tests total, clean `npm run build`.

## What was built in Phase 9A — employee identity and RBAC foundation (2026-08-13)

See the [Phase 9A engineering journal entry](../09-engineering-journal/), [docs/architecture/employee-platform.md](../architecture/employee-platform.md), and [ADR-006](../architecture/decisions/ADR-006-employee-identity-and-rbac.md) for full detail:

- A fifth backend service, `employee-service` (port 8085, `banksphere_employee` database), and a second frontend application, `employee-portal/` (port 5174) — BankSphere's first non-customer channel. Neither touches the four existing services' code, databases, or the existing customer frontend.
- The central design decision: employee JWTs are signed with `EMPLOYEE_JWT_SECRET`, a key wholly separate from customer-service's `JWT_SECRET` — considered and rejected the alternative of sharing one secret and distinguishing principal type by claim alone, since that would make "is this an employee token" depend on every current and future endpoint remembering to check a claim correctly, rather than on cryptography. Proven live: a real customer-service-issued JWT, presented to the real running employee-service, was rejected with a genuine `401` — not simulated, an actual cross-service HTTP call.
- `Role` (7 fixed roles) and `Permission` (20 fixed permissions) modeled separately, joined by a documented, code-defined `RolePermissions` mapping table, enforced server-side via Spring Security `@PreAuthorize` on every employee-management endpoint — the first use of Spring Security method security anywhere in this codebase.
- **A real bug found and fixed while writing the RBAC tests**: `GlobalExceptionHandler`'s existing catch-all exception handler (the same boilerplate every other service already had) was silently absorbing Spring Security's `AccessDeniedException` before `JwtAccessDeniedHandler` could turn it into the intended `403` — every `@PreAuthorize` rejection was instead surfacing as an unexplained `500`. No prior service had exercised this path (none use `@PreAuthorize`), so the bug had never had an opportunity to appear before.
- No public employee registration; a single seeded bootstrap `ADMIN` employee (documented local-dev-only credential) closes the resulting chicken-and-egg problem.
- Structured, correlation-id-tagged audit logging of every login attempt and employee-management action (`EmployeeAuditLog` + `CorrelationIdFilter`) — explicitly not the full Audit Service named in the roadmap, but the shape a future one can consume without reparsing free-text log lines.
- 57 new backend tests (28 more than any prior single-service phase) including a parameterized test authenticating as every non-`ADMIN` role in turn and confirming each is rejected, and a real-key unit test proving cross-service token rejection. 15 new frontend tests. Zero regressions: all four existing backend services (134 tests total) and the existing customer frontend (37 tests) re-verified passing, untouched.
- **Real end-to-end verification, both HTTP-level and browser-level**: rebuilt the actual employee-service Docker image, ran it against the project's live shared Postgres (which correctly created and migrated a fresh `banksphere_employee` database), and drove real `curl` calls proving login, permission-derived JWT claims, RBAC-denied employee creation (403 for a non-admin), successful admin-provisioned employee creation, `/me` returning no password field, and the cross-service rejection scenario above. Separately, with real browser tooling (`google-chrome` via `puppeteer-core`, the same method established in Phase 8A), drove the actual compiled `employee-portal` through a real login → profile → logout journey against the live service, confirming correct rendering of name/employee number/roles/branch/permissions, the correct (portal-specific) `localStorage` key, and zero console or page errors.

## What was built in Phase 9B — branch cash deposit (2026-08-13)

See the [Phase 9B engineering journal entry](../09-engineering-journal/), [docs/architecture/employee-operations.md](../architecture/employee-operations.md), and [ADR-007](../architecture/decisions/ADR-007-branch-cash-deposit.md) for full detail:

- The first real employee-initiated banking operation: a `TELLER`/`BRANCH_MANAGER` finds a customer (by account number or customer id), selects one of their accounts, and credits it with cash — a real account-service balance mutation (reusing the exact same `credit()`/`requireActive()` code path a customer's own deposit already used, not a parallel implementation) and a real transaction-service `DEPOSIT` ledger entry, described as "CASH DEPOSIT - Branch HQ001[, employee note]".
- A new "Employee Operations API" in employee-service (`GET /api/v1/operations/customer-search`, `POST /api/v1/operations/cash-deposits`, `GET /api/v1/operations/cash-deposits/history`), which orchestrates calls to account-service and customer-service by forwarding the acting employee's own bearer token to each — the same "downstream service independently re-verifies the caller's real token" pattern account-service has used calling transaction-service since Phase 1, extended to a second principal type rather than replaced with a new trust mechanism.
- **Real branch-scoped authorization, closing a gap Phase 9A explicitly deferred.** Investigated first (per the task's own instruction) whether `Account`/`Customer` had any existing branch relationship — neither did. Rather than inventing a new `branch_id` column on `Account`, the existing `accounts.ifsc` (Phase 8A) and `branches.ifsc` (Phase 9A) fields were used instead — the same relationship a real IFSC encodes in an actual bank. A `TELLER`'s employee JWT now carries a `branchIfsc` claim; account-service compares it against the target account's own IFSC and rejects a mismatch with `403`. `BRANCH_MANAGER`/`ADMIN` are explicitly exempted — documented, not an oversight.
- `CASH_DEPOSIT` reused exactly as Phase 9A's `RolePermissions` table already defined it (`TELLER`/`BRANCH_MANAGER` only) — inspected rather than assumed, and confirmed live: a KYC officer's real attempt to cash-deposit was rejected `403`; `ADMIN` — per the existing mapping — does not hold this permission either, matching ADR-006's original "don't give ADMIN unrestricted money-moving access" decision.
- Three more services gained the ability to independently validate employee-service-issued JWTs: account-service, transaction-service, and customer-service each got their own `EmployeeJwtValidator`/`EmployeeJwtAuthenticationFilter` pair (own key, `EMPLOYEE_JWT_SECRET`), running *alongside* — never replacing — their existing, byte-for-byte-unchanged customer-token filter. Proven live: a customer JWT sent to the new employee-only `cash-deposits` endpoint (employee-service) returned `401`; the same customer JWT sent directly to account-service's `employee-deposit` endpoint returned `403` — the correct 401-vs-403 distinction (authenticated-as-something-else vs. lacking permission), not a coincidence.
- **A real, minimal, carefully-scoped addition to employee-service's own database**: `cash_deposit_operations`, storing only immutable, point-in-time operational facts (which account, how much, by whom, when, plus the real transaction reference) — never mutable state like balance or customer name, both of which are resolved live from their owning service on every read instead. Only successful deposits are persisted; a failed attempt is captured in the structured audit log alone.
- `EmployeeAuditLog` extended with `CASH_DEPOSIT_STARTED`/`SUCCEEDED`/`FAILED` events, carrying branch/account/amount fields in addition to Phase 9A's existing employee/correlation-id fields.
- Employee-portal UI: Cash Operations landing page, a 5-step Cash Deposit wizard (find customer → select account → amount → review → confirm/success), and a Cash Deposit History table — the "Cash Operations" nav entry changed from an inert "Coming soon" badge to a real link for the first time.
- 74 new/changed backend tests across account-service (+45), customer-service (+2 net), transaction-service (+3), and employee-service (+26) — including a parameterized RBAC proof pinned against the real `RolePermissions` mapping, branch-scope violation/bypass tests, and a documented regression test for the one known rough edge (an employee token hitting an unmodified customer-only endpoint gets a `400`, not a clean `403` — see ADR-007). 9 new employee-portal tests. **Zero regressions**: customer-service (43), account-service (90 + 2 real-Postgres IT), transaction-service (15), beneficiary-service (25), employee-service (83) all still pass; the customer frontend's 37 tests and clean build are untouched, since no customer-frontend code changed at all this phase.
- **Real end-to-end verification at both the HTTP and browser layers.** Rebuilt all four changed backend images plus `employee-portal`, ran them against the live shared Postgres, and drove a complete `curl`-based flow: registered a real customer, opened a real account, logged in as the real seeded teller, searched for the customer by account number, performed a ₹10,000 cash deposit, and confirmed — via the customer's *own* authenticated calls to account-service/transaction-service, exactly what the customer portal itself calls — that the balance and a real, correctly-described transaction were both immediately visible. Separately, a real-browser Puppeteer session drove the actual compiled `employee-portal` through the full 5-step wizard to a real `CD-...`/`TXN-...` reference pair, then opened a second, independent browser tab logged into the actual compiled customer portal and confirmed the same balance and transaction there, then returned to the employee portal and confirmed the deposit appeared in Cash Deposit History. **22/22 checks passed, zero console or page errors.**

## Environment constraints hit during this work

- No local Java/Maven — all backend builds and tests run inside a `maven:3.9-eclipse-temurin-21` container.
- No `docker compose` (v1 or v2) binary available in any phase so far, and the install hosts were unreachable — the full stack is instead verified by building each Docker image individually and wiring them together by hand with `docker network`/`docker run`, matching `docker-compose.yml`'s service definitions (env vars, ports, network) exactly. This is equivalent to but not the same as running `docker compose up`, and was re-confirmed still true in Phase 3A.
- No browser available in any phase — frontend correctness was verified via `tsc -b`/`vite build`, a repo-wide static audit (unused imports/console.log/hardcoded values/missing alt text/broken links/overflow-prone classes), and a local dev-server + Docker container smoke test (HTTP status + SPA routing fallback checks — Phase 3C additionally `curl`-checked every one of its 8 new routes plus every pre-existing public route against a local `vite` dev server). Phase 1's review and Phase 3A additionally used `curl` against a live stack (CORS preflight in Phase 1; a full register → login → protected-call → cross-customer-denial flow with real JWTs in Phase 3A). Actual rendered/interactive UI, real mega-menu hover/keyboard behavior, and real animation timing were never seen in any phase — see the Phase 2 journal entry's limitations section. **Phase 8** is the first phase with a meaningfully stronger substitute: 29 Vitest + React Testing Library tests exercise real component rendering, real user interaction (typing, clicking, tab navigation, disabled-state timing) and real DOM assertions in `jsdom` — closer to a browser than any prior phase's static/curl-only checks, though still not an actual browser (no real layout/paint/CSS-cascade verification, no real click-vs-hover mouse behavior).
- Unlike every backend phase, **Node/npm were directly available in this environment** (no Docker-container workaround needed for `npm run build`/`npm test`, unlike the Java/Maven services).
- **Phase 8A is the first phase with real browser tooling available** (`google-chrome`/`chromium` installed) — used via `puppeteer-core` (pointed at the system Chrome binary, no bundled-browser download needed) from a throwaway scratchpad script to drive the actual compiled portal through a real user journey and capture real network traffic, console output, and page errors. This is a materially stronger verification method than any prior frontend phase had and was the deciding factor in finding this phase's real root cause. Not added as a project dependency — it's a diagnostic tool, not part of the shipped test suite (`npm test`'s Vitest/RTL suite remains the repo's actual, checked-in frontend test tooling).

## What was built in Phase 9C — Customer 360, KYC, and document verification (2026-08-14)

See the [Phase 9C engineering journal entry](../09-engineering-journal/), [docs/architecture/customer-360-and-kyc.md](../architecture/customer-360-and-kyc.md), and [ADR-008](../architecture/decisions/ADR-008-kyc-domain-and-document-storage.md) for full detail:

- A sixth backend service, `kyc-service` (port 8086, `banksphere_kyc` database) — BankSphere's first genuine bounded domain to expose a complete API surface directly to *both* portals (not proxied through employee-service, unlike cash deposit). Owns KYC applications, document metadata, document verification state, and review decisions; no cross-database foreign keys.
- A full customer KYC lifecycle (create → upload PAN/Identity Proof/Address Proof/Bank Statement → submit → resubmit if additional information is requested) and a full employee review lifecycle (queue → start-review → verify/reject each document → request-information or approve/reject), both funneled through one authoritative `KycStateMachine` table — every transition outside the locked-in `DRAFT → SUBMITTED → UNDER_REVIEW → {APPROVED, REJECTED, ADDITIONAL_INFORMATION_REQUIRED → RESUBMITTED → UNDER_REVIEW}` graph rejected with `422` regardless of which code path attempted it.
- `KYC_REJECT` added to the Phase 9A permission catalog (symmetric with the pre-existing, previously-unused `KYC_APPROVE`) — `KYC_VIEW`/`KYC_REVIEW`/`KYC_APPROVE` already existed but had never been used by any endpoint until this phase. `KYC_OFFICER` also gained `TRANSACTION_VIEW` (a real AML/KYC need). The mapping was inspected before any change, not assumed.
- A `DocumentStorage` interface + `LocalDocumentStorage` (filesystem-backed, a Docker named volume, UUID-generated filenames never the caller's own) — the KYC domain has zero direct dependency on AWS SDK classes anywhere; a future `S3DocumentStorage` is a drop-in replacement. `storageReference` never crosses into any customer- or employee-facing response.
- **A real concurrency bug found and fixed while writing this phase's own proof of the concurrency requirement.** `KycApplicationReviewConcurrencyIT` (a real-Postgres integration test, same pattern as `AccountTransferConcurrencyIT` since Phase 7A) simulates two officers racing to approve/reject the same application. The first run of this test revealed that `KycAuditLog` was logging `KYC_REJECTED ... result=SUCCESS` for the *losing* transaction a moment before the database actually rejected the write — every mutation was using `save()` instead of `saveAndFlush()`, so the optimistic-lock conflict wasn't detected until after the audit line had already been written. Fixed by switching every review-decision write to `saveAndFlush()`; the corrected test (and a rerun) show exactly one audit line, for the winning decision only.
- **Customer 360**: `GET /api/v1/employee/customers/{customerId}/360` in employee-service, aggregating five services live (customer-service, account-service, transaction-service, beneficiary-service, kyc-service) by forwarding the caller's own bearer token to each — no data copied into employee-service's own database. Introduces this codebase's first **section-level graceful degradation**: each of the five response sections is independently `{available, unavailableReason, data}` against the caller's actual permission set, rather than the usual all-or-nothing endpoint-level `403`. Fed by four new/extended employee-only endpoints: customer-service's additive `GET .../employee-lookup/{id}/profile`, transaction-service's new `GET /api/v1/transactions/employee/account/{accountId}` (its first `@PreAuthorize`-gated endpoint, upgrading its employee-token principal from a bare defensive string to a real `EmployeePrincipal`), beneficiary-service's new `GET /api/v1/beneficiaries/employee/customer/{customerId}` (this service's first-ever acceptance of an employee token at all — full `EmployeeJwtValidator`/`EmployeeJwtAuthenticationFilter` quartet added from scratch), and kyc-service's `GET /api/v1/kyc/employee/customer/{customerId}` (`204`, not `404`, when the customer never started KYC).
- **Two `AccessDeniedException`-handler gaps proactively closed before they could bite**: adding `@PreAuthorize` to transaction-service and beneficiary-service for the first time meant each needed the same explicit `AccessDeniedException → 403` handler ADR-006 found missing in employee-service during Phase 9A — added to both `GlobalExceptionHandler`s up front this time, not discovered by accident.
- Branch scope: KYC is **globally reviewable, not branch-scoped** — an explicit decision (see ADR-008, Decision 11), not an oversight: unlike `Account.ifsc` for cash deposit, a KYC application has no natural branch anchor, and inventing one would repeat the exact mistake ADR-007 rejected for `Account` itself.
- Customer portal: a new "KYC" nav item and single state-driven page (`pages/kyc/Kyc.tsx`) covering every application state, plus this codebase's first file-upload component (`components/forms/FileUpload.tsx`, built to the same label/hint/error contract as `Input`/`Select`).
- Employee portal: "Customer 360" (reusing the existing account-number search step) and "KYC & Compliance" — this portal's first nested-nav module (`AppLayout.tsx`'s nav rendering extended to support sub-items, each independently permission-filtered) — with KYC Queue, Document Verification (applications currently under review), Completed Reviews, and a Review Application screen doing real document verify/reject, request-information, and approve/reject actions, each gated inline on the caller's own `KYC_REVIEW`/`KYC_APPROVE`/`KYC_REJECT`.
- 66 new kyc-service tests (unit + `@WebMvcTest` controller + the real-Postgres concurrency IT), plus new/changed tests in customer-service, transaction-service, beneficiary-service, and employee-service. **348 backend tests passing across all six services, zero regressions** (account-service 90, customer-service 49, transaction-service 20, beneficiary-service 30, employee-service 93, kyc-service 66). Both frontends build clean (`tsc -b && vite build`) with zero regressions in existing tests (37 customer-portal, 24 employee-portal) — no new frontend tests were added this phase (time-constrained; noted as a real gap, not claimed otherwise).
- **Real end-to-end verification at both the HTTP and browser layers.** Rebuilt all six backend images plus both frontends by hand (no `docker compose` binary available in this environment, same constraint noted in every prior phase — each image built and wired with `docker network`/`docker run` individually, matching `docker-compose.yml`'s definitions exactly) and ran the full stack against the live shared Postgres. Drove a complete `curl` flow: customer registration → KYC application creation → all 4 document uploads → submission → employee login → queue → start-review → all 4 documents verified → approval → customer's own `GET /me` immediately showing `APPROVED`; plus explicit negative checks: a second customer denied `403` reading the first customer's application by UUID, a `TELLER` (lacking `KYC_APPROVE`) denied `403` approving, a customer token denied `403` on an employee-only endpoint, no token `401`, submitting with zero documents `422` with the exact missing-types list, approving a `DRAFT` application directly `422`, a duplicate active application `409`. Separately, a real-browser Puppeteer session drove both actual compiled portals through the complete journey — register, log in, start a KYC application, upload all 4 documents (via real native file inputs), submit, then a second browser tab logged into the employee portal, opened the KYC Queue, opened the review screen, started review, verified all 4 documents, and approved the application, with the review screen showing the real, correctly-ordered status history (`DRAFT → SUBMITTED → UNDER_REVIEW → APPROVED`). (A scripting bug in the E2E harness itself — stale Puppeteer element handles across a React re-render after each document upload — was found and fixed mid-run; the final customer-sees-APPROVED reload step was independently confirmed via the `curl` flow above after the harness's own final step hit an unrelated `networkidle0` timeout waiting on a persistent widget connection, not an application defect.)

## What was built in Phase 9D — customer OTP authentication + step-up authentication (2026-08-14)

See the [Phase 9D engineering journal entry](../09-engineering-journal/), [docs/architecture/customer-authentication.md](../architecture/customer-authentication.md), and [ADR-009](../architecture/decisions/ADR-009-customer-otp-and-step-up-authentication.md) for full detail:

- Customer OTP login (`POST /api/v1/auth/otp/{request,verify}`), additive alongside the existing password login — issues the identical `AuthResponse` shape; the request-OTP response is deliberately generic (never reveals whether `identifier` matched a real, enabled customer), extending the exact same timing-safe-comparison pattern `AuthServiceImpl.login()` already used for password login.
- Refresh tokens: opaque 256-bit random values, SHA-256-hashed at rest, delivered exclusively via an HttpOnly/`SameSite=Lax`/path-scoped cookie (`banksphere_refresh_token`) — never in a JSON body or `localStorage`. Rotated on every `POST /api/v1/auth/token/refresh`; reusing an already-rotated token revokes the customer's entire token family.
- **A real security bug found via live Docker verification, not by any unit test, and fixed before shipping.** The family-wide revocation on reuse detection was originally mutating entities inside the same `@Transactional` method that then threw the rejection exception — Spring's default rollback-on-`RuntimeException` behavior silently undid the revocation every time, so a stolen token's sibling sessions stayed valid. Caught by curling a real running container through the exact reuse sequence and inspecting `refresh_tokens` in the database directly afterward — the mocked unit tests had no way to surface this, since they never exercised a real Spring transaction boundary. Fixed by extracting the revocation into `RefreshTokenRevocationService`, a separate bean with its own `REQUIRES_NEW` transaction — the identical pattern account-service's `TransferIdempotencyService` already used for its own bookkeeping, applied here for the first time in customer-service. Re-verified live: the fix holds.
- Step-up authentication for transfers at/above a configurable threshold (default ₹50,000): `POST /api/v1/auth/step-up/{request,verify}` (customer-service) + `POST /api/v1/auth/step-up/confirm` (called by account-service, forwarding the customer's own bearer token — the same "downstream service re-verifies the caller's real token" pattern this codebase has used since Phase 1). A step-up challenge is bound to the exact operation via a SHA-256 hash (`OtpContextHasher`) over its canonical fields (source account, destination, amount, currency) — recomputed and compared at confirmation time, so amount/recipient tampering after OTP verification is rejected with `403`, never silently allowed.
- `POST /api/v1/accounts/transfer`'s existing atomicity/locking/ledger design (ADR-004) is completely unchanged; it is now wrapped with an optional idempotency mechanism (`TransferIdempotencyService`, a real database `UNIQUE (customer_id, idempotency_key)` constraint as the actual exactly-once enforcement, not just the application-layer pre-check) and gated by `StepUpPolicy` before any balance mutation.
- A local-development-only OTP inbox (`GET /api/v1/auth/dev/otp-inbox`) whose controller bean is proven — via an `ApplicationContextRunner` test, not just asserted — to not exist in the application context at all unless explicitly enabled.
- Customer portal: a "Password" / "One-time code" tab on the existing Login page (password path byte-for-byte unchanged); a reusable `StepUpOtpModal` wired into the Transfer flow, opening on the backend's `403` and never deciding on its own that step-up is satisfied; a dev-only OTP inbox panel reused in both places.
- 118 customer-service tests + 113 account-service tests (new/changed, including full coverage of OTP generation/expiration/security/login/step-up/idempotency scenarios), **zero regressions across employee-service (93), transaction-service (20), beneficiary-service (30), and kyc-service (65) — 439 backend tests passing across all six services.** Both frontends build clean; customer frontend gained 6 new tests (Login OTP flows, Transfer step-up flow with tampering/replay assertions at the mock level) for 43 total, zero regressions; employee-portal untouched (24 tests, customer-facing phase only).
- **Real end-to-end verification via live Docker containers with direct database inspection**, not just curl-status-code checks: registered a customer, logged in via OTP (retrieving the code from the dev inbox), created two accounts, and drove all five of the phase's required flows — login, invalid/replayed OTP rejected, transfer step-up (request → verify → confirm → execute exactly once), replay of an already-executed step-up challenge rejected with no second transfer, and tampering (amount changed after verification) rejected with no balance mutation — plus idempotency (identical double-submitted request returns the identical cached result, balance moves exactly once) and the full refresh-token rotation/reuse-detection/logout lifecycle, confirmed against `refresh_tokens` table state directly, not just HTTP status codes.
- **No real browser (Puppeteer/Playwright) E2E run this phase** — no such tooling installed in this environment, unlike Phase 8A onward where `puppeteer-core` pointed at the system Chrome was available and used. Documented honestly here rather than claimed: the equivalent ground was covered by real HTTP calls against live, rebuilt Docker containers (proving backend correctness, real `Set-Cookie`/CORS headers, and real database state) plus Vitest component tests simulating the same user interactions (typing, clicking, tab-switching) against a mocked API layer (proving frontend wiring correctness). What a real browser run would add beyond that — genuine cross-origin cookie behavior enforced by an actual browser's CORS/cookie engine rather than curl or jsdom — was not verified this phase.
